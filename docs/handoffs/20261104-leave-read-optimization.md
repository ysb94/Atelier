# 연차 조회 중복 처리·잠금 축소 검증

상태: **로컬 검증·승인된 함수 4개 공유 DB 적용·보존 검증 완료**. 원격 이력 `20261104071756_leave_read_reconciliation_efficiency`(로컬 파일명은 준비 시각 유지). test/main 사이트 배포는 하지 않았다.

대상: `20261104061531_leave_read_reconciliation_efficiency.sql`의 기존 함수 4개만 보완한다. 테이블·열·권한·예약 실행 주기를 추가하거나 변경하지 않는다.

| 함수 | 변경 |
| --- | --- |
| `app.ensure_employee_birthday_leave` | 실제 생일 부여가 필요한지 읽기로 확인한 뒤에만 직원 잠금을 얻는다. 잠금 대기 후 자격을 다시 확인하고 기존 고유키로 중복을 막는다. 취소한 생일분은 재부여하지 않는다. |
| `app.record_leave_expiry` | 기록해야 할 만료 차액이 없으면 잠금 없이 반환한다. 차액이 있으면 잠금을 얻은 뒤 잔여·기존 이력을 처음부터 다시 계산한다. |
| `app.refresh_employee_leave_before_birthday` | 같은 잠금 안에서 기본 연차 기간과 잔여가 변하지 않았다고 확인한 경우에만 두 번째 동일 예산 계산을 생략한다. 월별 증가·연차 초기화는 두 계산을 유지한다. |
| `app.employee_extra_leave_records` | 바로 덮어쓰던 중간 잔여 목록을 만들지 않고 최종 응답을 한 번 계산한다. UUID 한 번 순회 안에서 직원별 생일→만료를 처리해 다른 관리자 조회와 잠금 순서를 맞춘다. 기존 관리자·회사 확인과 응답 필드는 유지한다. |

TTL·별도 캐시를 쓰지 않으며 매 조회 시 생일·만료의 누락 여부를 확인한다. 기본/추가 기한순 차감, 신청·취소·부여 취소·선사용·음수 처리 규칙은 변경하지 않는다.

## 검증

Node 22에서 실행:

```powershell
node scripts/verify-leave-balance-db.mjs --anniversary --additional --fefo --birthday --advance --load-guard --read-efficiency
node scripts/verify-leave-read-concurrency.mjs
```

- 기존 연차·생일·FEFO·선사용 회귀와 새 함수 상태 비교 28개 통과. 기존 날짜 요약 비교 250개도 통과했다.
- 새 함수 적용 자체가 직원·명부·신청·부여·배분·선사용·이력을 바꾸지 않는지 비교했다. 기존 함수 OID·소유자·ACL·보안 속성과 모든 RLS 정책도 동일했다.
- 생일 ±7일·윤년/연말·미등록/퇴사/미승인·부여 취소, 월별 증가/기간 초기화·음수/미등록 잔여, 만료/조정/반복, 취소 후 만료분 미복원 및 조회 권한을 검증했다.
- PostgreSQL 18.3의 새 임시 DB에서 실제 동시 연결 8개 시나리오를 통과했다. 생일 동시 부여와 만료 동시 처리가 각각 한 번만 기록되고, 잠금 대기 중 자격·잔여 변경도 다시 계산한다. 이미 반영된 생일/만료 조회는 직원 잠금이 다른 연결에 잡혀 있어도 완료된다. 같은 조건의 기존 함수는 350ms 제한에 걸렸다.
- 생일·만료를 별도 순회하던 초기 최적화안은 A 직원의 만료와 B 직원의 생일이 겹칠 때 관리자 선사용 조회와 잠금 순서가 뒤집혔다. 실제 두 연결에서 교착 오류 `40P01`을 재현하고, 한 번의 UUID 순회로 고친 뒤 두 조회가 완료되며 생일·만료 이력도 한 번만 남는 것을 확인했다. 이 시험은 실제 두 관리자 조회 함수와 잠금 순서를 보존한 최소 갱신 fixture를 사용하며, 금액·선사용 계산 전체는 앞의 PGlite 회귀에서 검증한다.
- 로컬 시험 서버는 종료했으며 운영 DB에 시험 데이터를 쓰지 않았다.

## 측정 범위

합성 PGlite 데이터 기준 한 번의 조회:

| 조회 | 기존 | 변경 |
| --- | --- | --- |
| 일반 직원 본인 선사용/잔여 조회의 기본 예산 계산 | 2회 | 1회 |
| 위 본인 조회의 대상 함수 내 직원 잠금 요청 | 4회 | 1회 |
| 관리자 35명 추가 연차 조회의 가용량 계산 | 70회 | 35회 |
| 위 관리자 조회의 대상 함수 내 직원 잠금 요청 | 70회 | 0회 |

두 조회 모두 변경 없는 반복 호출의 행 쓰기는 0회였다. 표의 잠금 수는 변경 대상 함수만 계측한 값이며 전체 호출 체인의 모든 잠금을 없앴다는 뜻이 아니다. 잠금 순서 보완 후 로컬 표본 실행시간은 본인 2.47→2.43ms, 관리자 8.29→6.53ms였고, 전체 검증 재실행에서는 각각 2.43→2.53ms, 9.80→9.06ms였다. 실행마다 차이가 있어 일반 직원의 실제 응답시간 개선은 아직 입증하지 않았으며, 감소한 계산·잠금 요청 수만 확정된 결과다. 실제 적용 후 일반 직원과 관리자 화면에서 별도 확인이 필요하다.

## 적용·복구

대상 함수 4개와 기존 조회 래퍼 `app.employee_extra_leave_records_before_fefo()`·`app.employee_extra_leave_records_before_birthday()`까지 원본 정의를 대조했다. 초기 연결 실패 후 사용자가 재시작했고, 서비스 정상화를 확인한 다음 승인 범위만 적용했다.

적용 직전 대상 함수 4개와 기존 조회 래퍼 2개의 정의를 대조하고 기존 정의·함수 권한을 보관한다. 기존 정의가 달라졌다면 자동 적용하지 않는다. 새 migration은 함수 정의만 교체하며 기존 데이터를 일괄 보정하지 않는다. 문제가 생기면 보관한 원본 함수 4개를 복구한다. 함수 복구 때문에 연차 원본·정상 처리 이력을 되돌리지 않는다.

적용 SQL은 REPEATABLE READ에서 원본 6개 정의 일치 확인 → 원본 13개 표·보안 속성 fingerprint → 4개 교체 → 같은 표·속성 보존 및 정확히 4개 정의 변경 확인 → COMMIT으로 실행했다. 함수 OID·소유자·실행 권한·보안 설정·RLS와 기존 업무 데이터 보존을 확인했다.

적용 후 실제 authenticated 역할의 일반 직원 본인 조회는 약 75ms, 근태 기준은 약 6ms에 완료했다. 관리자 반환(잔여 37명·추가 부여 3건)은 기존 래퍼 전체 JSON과 같고 같은 회사 범위였으며, 일반 직원의 관리자 조회는 기존처럼 42501로 거부됐다. 검증은 모두 ROLLBACK하여 시험 처리를 저장하지 않았다. 표본 속도 자체는 개선율 근거로 삼지 않는다. 서버 메모리·IO 진단과 별도 승인된 컴퓨트 변경은 [조회 최적화 기록](../architecture/READ_LOADING_OPTIMIZATION.md)을 따른다.
