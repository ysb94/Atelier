# 신규직원 가입 승인과 입사 처리

## 화면과 권한

- 가입 승인 위치는 `운영지원 → 조직도 → 신규직원`의 `승인여부 → 관리` 한 곳이다. 직접 주소는 `/operations-support?part=org&orgView=new`이며 새로고침·멤버 화면의 연결에도 같은 보기가 열린다.
- 같은 회사의 활성 운영지원부서 직원 전체가 직책·개인 인사 관리 지정 없이 승인·거절한다. 기존 가입 승인 지정자의 권한은 유지하며, 입사 개인정보·서류 열람 권한은 별도로 확인한다.
- 승인창은 본명·팀·직책·직급·입사일만 확인한다. 회사 입력정보 창에서는 근무·급여·계약 자료만 저장하며 승인 버튼을 중복 제공하지 않는다.
- 미리보기, 계정/세션 불일치, 비활성 계정, 타 회사·일반 직원, 숨겨진 작업 탭은 승인하지 못한다. 서버가 실제 로그인 직원과 회사·처리 시각을 판단한다.
- 멤버에는 사용 중·정지된 기존 계정만 표시한다. 정보 저장 시 승인 상태·승인자·승인 시각을 변경하거나 정지 계정을 재활성화하지 않는다. 정지·해제는 기존 직원 관리 권한을 유지한다.

## 누락 방지와 목록

- 같은 회사의 `profiles` 가입 대기·거절 상태와 온보딩 기록을 직원 ID로 연결한다. 신청 시각이나 서류 관리 기록이 없어도 대기자를 표시하고 실제 대기자는 위쪽에 둔다. 다른 회사 신청은 포함하지 않는다.
- 가입 대기·입사 처리 목록은 부서 배치나 본사 근태 관리 대상 필터로 숨기지 않는다. 기존 근태·연차 관리 대상 설정은 변경하지 않는다. 개발자 테스트 기록은 실제 가입 신청과 분리한다.
- 승인하면 서류 기록을 연결하고, 배치 후에도 `completedAt`이 없으면 진행 중에 남는다. 승인 자체를 입사 서류 완료로 기록하지 않는다. 완료와 되돌리기는 기존 온보딩 흐름을 사용한다.
- 거절은 거절 목록에서 표시한다. 기존 제출 정보·첨부·회사 입력정보를 삭제하지 않고, 재신청하면 같은 직원의 최신 대기 상태를 사용한다. 가입 대기자는 완료 목록에 묻히지 않으며 승인 전 완료 버튼은 제공하지 않는다.
- 저장 후 가입 대기·입사 기록·조직도·명부·회사 정보·기존 계정 조회를 함께 갱신한다. 현재 보이는 화면은 30초 주기로 최신 상태를 확인하며 창 포커스 재조회는 사용하지 않는다.
- 기존 코드에 가입 승인 전용 서버 알림·읽음 기록은 없으므로 별도 로컬 읽음이나 중복 알림을 만들지 않는다. 멤버의 가입 승인 안내 링크는 신규직원 보기로 직접 연결한다.

## 서버 처리

추가 마이그레이션은 `20261105092213_employee_access_onboarding_review.sql`이다. 새 함수 `public.review_employee_access`는 invoker 래퍼이고, 실제 처리는 비공개 `app.review_employee_access`에서 한다. 둘 다 익명·PUBLIC 실행을 회수하고 authenticated 실행만 명시적으로 허용한다. 기존 함수·트리거·표·정책·기존 운영 클라이언트는 교체하지 않는다.

적용 끝에 PostgREST 스키마 캐시 새로고침 신호를 보낸다. 새 함수의 API 연결은 [Supabase 스키마 캐시 갱신 안내](https://supabase.com/kb/troubleshooting/refresh-postgrest-schema)를 따른다.

- `check`는 개인정보 없이 서버 준비와 현재 직원의 가입 승인 가능 여부만 확인한다. 미적용 시 화면에 `가입 승인 서버 연결 대기`를 표시하고 승인·거절을 비활성화한다.
- 승인·거절은 활성 직원·회사·기존 승인 권한을 검사하고 같은 회사의 가입 대기자 프로필을 잠근다. 자기 승인, 타 회사, 이미 처리한 대상, 잘못된 입력을 차단한다. 관리자가 먼저 처리한 경우 `40001`로 최신 상태 조회를 안내한다.
- 승인 시 서류 관리 기록이 없는 대상은 한 건만 생성한다. 준비된 회사 정보가 있으면 이번 승인창의 배치·입사일과 맞추고 기존 회사 정보 저장 함수를 사용한다. 근무·급여 입력은 보존한다. 프로필 승인까지 같은 트랜잭션이므로 중간 오류 시 기록 생성·버전·명부·승인 변경이 함께 롤백된다.
- 거절 시 승인 상태·처리자·처리 시각만 변경한다. 관리자·이메일·역량·브랜드·기능 지정 권한을 입력받거나 변경하지 않는다. 가입 신청 원래 시각도 보존한다.
- 진단은 입력 검사 → 권한/서버 확인 → DB 처리 → 관련 조회 갱신을 추적한다. SQLSTATE를 보존하고 저장 성공 뒤 화면 갱신 실패는 `writeOutcome: committed`로 구분한다. 재전송하지 않으며 선처리·저장 후 갱신 오류에서는 재승인을 막는다.

## 검증과 적용

- `npm run verify:employee-access`: 누락·중복·상태별 목록, 실제 SQL의 승인/거절·준비 정보 연결·롤백·권한/회사/익명 차단, 실제 SDK와 UI의 화면 이동·중복 클릭·선처리·서버 미적용·오류·PC/모바일·계정 전환·미리보기·숨겨진 탭을 가상 데이터로 검사한다.
- `node scripts/verify-employee-onboarding-browser.mjs`: 기존 직원 정보·파일 업로드·출력·완료·되돌리기를 회귀 검사한다. 브라우저 fixture는 외부 통신을 차단하며 공유 DB·실제 직원을 시험 변경하지 않는다.
- 적용 전에는 기존 정의·정책·트리거·원본의 요약 해시를 `docs/backups/employee-access-review-before-20261105.json`에 보관한다. 개인정보 본문이나 원본 파일은 내려받지 않으며 백업·실행 기록은 커밋하지 않는다.
- 2026-11-05: 공유 DB는 읽기 전용으로 확인했고, 새 API는 아직 없다. 새 함수 2개의 공유 DB 적용과 main 배포는 별도 승인 단계다. 새 API를 적용하기 전에도 기존 운영 화면·승인 함수는 유지된다.
- Node 22.23.3에서 전용 검증(목록·격리 SQL·실제 SDK 브라우저), 기존 온보딩 브라우저, 전체 권한·공개 범위·기존 승인 DB·워크스페이스 탭·diagnostics·workflow diagnostics(브라우저 포함), lint, 전체 build와 구조 목차 9검사가 통과했다. 검증용 외부 통신과 공유 DB 시험 변경은 없었다.
- 서버 저장 실패, 서버 미적용, 다른 담당자 선처리, 저장 후 조회 실패, 미리보기·계정 전환·숨겨진 탭, 서류 열람 권한 해제 후 캐시·상세 차단을 확인했다. 의도한 오류는 진단 코드와 처리 단계로 구분되며 브라우저의 미처리 오류·렌더/조회 폭주·외부 요청은 없었다.
