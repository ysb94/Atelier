# 화면 테스트 점검 (2026-10-20)

개발자·대표이사의 상단 `화면 테스트`에서 페이지의 실제 표시 분기를 선택한다.
기존 목록(`page-preview-cases.ts`)은 보존하고 `page-preview-coverage.ts`에서
누락을 보완한다. Cursor가 먼저 수정한 My home·역할 구분도 유지한다.

| 화면 | 시험하는 구분 |
| --- | --- |
| 홈 | 대표, 팀장, 사원, 운영지원 사원, 인사 담당, 출퇴근 제외 이사, 소속 미지정, 기획·디자인·MD·물류·데이터 담당 |
| My home | 팀장·사원·대표·이사, 소속 미지정, 직책과 별개인 부서 승인 담당 지정·미지정 |
| 부서별 작업 요청 4종 | 해당 부서 관리자·사원·다른 부서 요청자 (기존 목록 유지) |
| 기획안 | 담당자별 조회 가능·불가, 대표 검수 |

| 멤버·권한 | 인사·조직 수정 모두 가능, 인사만 가능, 관리자, 범위가 있어도 사원은 제한, 대표 조회 |
| 브랜드 관리 | 대표 조회, 대표이면서 관리자, 대표이면서 브랜드 책임자, 일반 관리자·책임자·직원 접근 제한 |

| 회의 | 관리자·직원, 주최자·참여자·비참여자·자료 등록자 |

| 공통 채팅·별도 채팅 창 | 팀장(다른 사람 메시지 삭제 표시), 관리자(저장소 현황), 사원 |

상단 테스트 버튼은 가로로 스크롤한다. 메뉴의 권한별 표시도 선택한 역할에 맞춘다.
원래 계정으로 돌아가려면 `종료`를 누른다. 페이지를 이동하면 선택을 적용하지 않는다.
숨긴 KeepAlive 탭에는 현재 페이지의 표시 프로필을 전달하지 않는다.

채팅 역할 버튼은 공통 상단에 표시하지 않는다. 채팅 패널을 열었을 때 그 패널 안과
별도 채팅 창에서만 `채팅 화면 테스트`로 표시한다. 별도 Provider를 사용하므로 페이지의
화면 테스트 선택을 바꾸지 않는다. 패널을 닫거나 알림으로 전환하면 채팅 테스트도
언마운트되어 사라지고, 다시 열면 실제 계정 상태에서 시작한다. 기존 채팅 권한은 유지한다.

채팅·알림 패널은 `document.body`의 Portal에서 공통 팝업 레이어(`z-index: 200`)로
표시한다. 상단 탭(`20`)의 자식으로 두면 상품 데이터 고정 헤더(`20`/`30`)에 가려져,
패널의 숫자만 높여서는 해결되지 않는다. 바깥 클릭 판정은 버튼 영역과 Portal 영역을
모두 확인한다. 브라우저 검증은 실제 `SheetTable` 헤더와 패널이 겹치는 좌표에서
수정 전 실패를 재현했고, 수정 후 가로·세로 스크롤과 내부 클릭·닫기까지 확인했다.

## 표시와 실제 데이터의 경계

- 프로필 ID·세션·인증 토큰은 바꾸지 않는다. 다른 직원의 데이터를 대신 조회하지 않는다.
- 업체 권한은 API 응답을 복사한 표시 값만 바꾼다. Query 캐시의 실제 권한은 보존하고,
  저장 함수에서 원래 업체·권한을 다시 확인한다. DB 미준비/조회 실패도 그대로 유지한다.
- 브랜드·AI의 새 편집 조합은 로그인 계정 권한을 별도로 확인한다.
- 본인 신청을 다른 직원 화면으로 표시해도 실제 승인·반려는 막고 이유를 표시한다.
- 지정 부서·신청 목록·공지 내용은 로그인 계정으로 조회한 실제 데이터다. 담당자 표시를
  선택해도 담당 부서가 실제 지정되지 않았다면 빈 목록/안내가 나온다. 임의 업무 데이터를
  생성하거나 실제 승인 담당자를 지정하지 않는다.
- 회의는 현재 기존 코드가 만드는 로컬 예시 회의 목록에서 관계만 선택한다.
  자료 등록자 모드는 첫 자료의 등록자를 사용하며, 자료가 없으면 원래 표시 인물을 유지한다.
- 공모전의 제한 화면은 테스트 중 페이지 이동 대신 안내로 보여 다시 전환할 수 있다.
  실제 접근 불가 사용자의 홈 이동 동작은 유지한다.
- 테스트에서 실제 저장 가능한 계정으로 저장하면 업무 데이터가 저장되는 기존 방식이다.
  가상 데이터 전용 샌드박스가 아니다. DB·RLS·마이그레이션 변경은 없다.

## 역할별 차이가 없는 화면

현재 라우트와 Auth/권한 사용처를 조사했다. 일반 조직도는 `mode=chart`라 편집 분기가 없고,
조직 편집은 운영지원에서 시험한다. 상품·SKU·기획안 편집·샘플 작업 지시서·디자인·물류·
데이터 업로드 등의 화면에서는 작성자 이름/개인 저장 목록을 위한 ID 사용과 업무 조건
(선택 브랜드 수, 진행 단계, 업로드 유무 등)을 역할에 따른 표시 분기와 구분했다.
로그인·가입/승인 대기는 회사 작업장 진입 전 인증 화면으로, 로그인 상태를 위조하지 않는다.

앞으로 새 역할 분기를 만들면 기본 목록 또는 보완 목록과 검증을 함께 갱신한다.
기존 역할이 실제로 다르게 판단되는지는 권한 함수와 실제 화면 양쪽으로 검증한다.

## 검증 명령

Node 22에서 실행한다.

```sh
npm run verify:page-preview
npm run verify:page-preview-browser
npm run verify:company-capabilities
npm run verify:work-request-roles
npm run verify:workspace-tabs
npm run verify:company-paths
npm run verify:diagnostics
npm run verify:structure-map
npm run build
```

브라우저 검증은 별도 로컬 서버에서 실제 컴포넌트와 오프라인 Auth/데이터를 사용한다.
환경 파일은 읽지 않고 외부 요청은 차단한다. 권한 전환, 메뉴, 숨긴 탭 격리,
대표/개발자 노출과 일반 직원 비노출, 실제 본인 승인 및 조회자의 업체 저장 금지를 확인한다.
운영 데이터 변경은 없다. 구조도는 `npm run structure:map`으로 갱신한다.
