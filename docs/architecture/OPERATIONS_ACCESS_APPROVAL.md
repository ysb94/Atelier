# 운영지원부서 가입 승인 검사

## 동작과 범위

- 회사의 활성 운영지원부서 직원은 직책이나 개인 인사 관리 권한 없이 다른 가입 대기자를 승인·거절한다. 특정 직원 ID 예외는 추가하지 않는다.
- 기존 `canReviewMember` 화면 조건과 `profiles_operations_access_decision` 정책을 유지한다. 기존 직원 관리, 관리자 지정, 기능 권한 지정은 별도 권한이다.
- 승인·거절은 기존 `approveMember`/`rejectMember`의 프로필 UPDATE를 사용한다. 입력·목록·새로고침 흐름은 바꾸지 않는다.

## 오류 원인과 수정

`app.guard_profile_changes()`가 운영지원의 가입 승인 검사보다 조직 정보 편집 검사를 먼저 실행했다. 두 권한을 가진 부서원이 승인 상태를 바꾸면 조직 정보만 수정할 수 있다는 예외가 발생했다.

`20261105065548_operations_access_approval_guard_order.sql`은 가입 대기 승인·거절 검사를 조직 정보 편집 제한 앞으로 옮긴다. 대상의 기존 회사와 변경 후 회사가 모두 같은 운영 회사일 때만 이 경로를 사용한다. 기존 관리자·자기 프로필·인사 관리·본명 확인·직책·직급·입사일 검사는 보존한다. 표, 정책, 함수 실행 권한, 기존 프로필 원본은 변경하지 않는다.

`20261105070652_operations_access_approval_department_guard.sql`은 승인 시 지정하는 부서도 같은 회사의 활성 부서인지 검사한다. 부서 미선택은 계속 허용한다. 기존 함수의 승인 검사 구간에 이 조건만 추가하며, 예상 구간이 없으면 중단하고 재적용은 중복 추가 없이 끝낸다.

## 검증

`npm run verify:operations-access-approval`은 외부 DB에 연결하지 않고 실제 SQL 트리거와 RLS를 실행한다. 수정 전 오류 재현, 수정 재적용, 원본·정책·권한 보존, 운영지원 승인·거절, 관리자·이메일·회사 변경·본명 확인 해제 차단, 비활성·타 부서·자기 승인 차단을 검사한다. 타 회사 직원과 타 회사 신청의 양방향 차단도 검사한다.

`supabase/tests/operations_access_approval.sql`은 같은 검사를 실제 `authenticated` 역할로 실행한다. 현재 활성 운영지원 계정은 인증 문맥으로만 사용하고 가상 운영지원 직원과 가상 가입 신청을 만든다. 성공·실패에 관계없이 가상 Auth 계정·프로필과 관련 기록을 하위 트랜잭션으로 롤백한다. 기존 직원이나 실제 대기 신청은 변경하지 않는다.

적용 전 함수 본문·소유자·실행 권한·프로필 정책·트리거와 사용자 원본의 요약 해시를 `docs/backups/operations-access-approval-before-20261105.json`에 보관한다. 복구용 이전 함수는 같은 폴더의 `operations-access-approval-rollback-20261105.sql`에 둔다. 백업과 실행 증거는 커밋하지 않는다.

## 적용 기록

- 2026-11-05 사용자가 운영지원부서 전체 수정과 공유 Supabase DB 적용을 명시적으로 승인했다.
- 공유 DB에 원격 `20261105070234_operations_access_approval_guard_order`를 적용했다. 적용 직전 함수 해시를 다시 검사해 다른 변경이 있으면 적용을 중단하도록 했다.
- 이어 원격 `20261105070802_operations_access_approval_department_guard`를 적용하고, 부서를 비운 승인과 유효 부서 지정 승인이 모두 성공하며 잘못된 부서·타 회사 부서·비활성 부서가 차단되는지 검증했다.
- 실제 활성 운영지원 계정 1명과 가상 운영지원 직원의 승인·거절이 모두 통과했다. 관리자·이메일·회사·본명 확인 변경, 비활성·타 부서·자기 승인은 차단됐다. 가상 Auth/프로필 잔여 건수는 모두 0이며 실제 대기 신청은 그대로다.
- 기존 프로필 39건의 전체 행 해시, 역량·브랜드 연결 해시, 프로필 RLS·트리거·표 권한과 함수 소유자·실행 권한·설정이 모두 보존됐다. 검증 중 실제 로그인·세션 갱신이 있으므로 Auth 전체 행 해시는 보존 판정에서 제외했다. Auth 계정 수는 39건으로 같고, 검증은 기존 Auth 행을 UPDATE하지 않는다.
- 보안 점검의 기존 항목별 건수는 적용 전후 동일하며 새로운 항목은 없다. 익명의 운영지원 확인 함수 실행은 차단되고 인증 역할만 허용된다.
- Node 22.23.3: 가입 승인 DB 검증, 운영지원 화면 권한 검증, 공개 범위 검증, diagnostics·workflow diagnostics(브라우저 포함), lint, 전체 build, 구조 목차 9검사 통과. `verify:company-capabilities` 전체 실행은 기존 `assigned-permissions.verify.ts:25`의 디자인 업무 `manager`/`requester` 불일치 1건으로 실패했다. 이번 변경의 운영지원 검증은 별도로 실행해 통과했고 해당 디자인 권한 코드는 수정하지 않았다.
- 2026-11-05 후속 테스트 정리: 사용자 요청으로 `assigned-permissions.verify.ts`의 예시 회사·부서 번호를 `RELEASE_COMPANY_ID`와 `WORK_REQUEST_DEPARTMENT_IDS`로 맞췄다. 다른 부서에서 디자인 관리 권한을 받은 경우와 다른 회사·비활성·미지정·예전 부서 문자열의 차단을 검증했으며, `verify:company-capabilities` 전체와 `verify:release-access`가 통과해 앞선 테스트 실패가 해소됐다. Node 22에서 전체 build·lint·구조 목차 9검사도 통과했다. 실제 업무 권한과 공유 DB 변경은 없다.
