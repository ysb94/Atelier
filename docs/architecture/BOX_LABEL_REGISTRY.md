# 박스 개별 라벨 발급 기록

2026-11-10 사용자 요청: 발급한 번호를 저장해 여러 컴퓨터의 반복 발급에서 중복을 막고 기존 번호를 재출력한다.

## 사용 흐름

- 창고관리 → QR 생성 → 박스 개별 라벨링 → 개수 입력 → **새 번호 발급·저장**. 서버 저장에 성공한 번호만 60×40mm 라벨로 출력한다.
- `ENJ-YYMMDD-숫자10자리`를 서버의 한국 날짜로 발급한다. 숫자 앞의 0도 유지한다.
- 같은 브랜드의 발급 내역을 다른 컴퓨터에서 조회하고, 묶음 전체 또는 전체 번호 검색으로 한 번호를 재출력한다. 재출력은 새 번호 발급이나 재고 등록을 하지 않는다.
- 이전 버전에서 인쇄한 번호는 **기존 번호 등록·저장**으로 공용 기록에 가져온다. 이전 브라우저 캐시는 입력 후보일 뿐이며 저장이 확인되기 전에는 출력하지 않는다. 동일 목록을 서버에서 확인한 뒤에만 이전 캐시를 지운다.
- 기존 번호를 다시 등록하려 하면 중복을 안내하고 저장 전체를 취소한다. 이미 등록한 번호는 발급 내역에서 불러온다.

## 저장과 권한

- 공유 Atelier DB에 `20261110062508_warehouse_box_label_registry.sql` 적용 완료. `20261110062749_warehouse_box_label_lookup_index.sql`로 묶음·브랜드 복합 참조 인덱스도 적용했다. 기존 재고·자리·출퇴근 자료는 변경하지 않는다. 운영 화면(main) 배포는 별도 단계다.
- `warehouse_box_label_batches`: 요청 UUID, 브랜드, 발급자, 시각, 발급 방식, 개수. `(brand_id, request_id)` 고유.
- `warehouse_box_labels`: 실제 QR 문자열, 발급 묶음, 브랜드, 순서. `code` 전체 고유. 동일 문자열을 다른 브랜드에서도 재발급하지 않는다.
- 번호 생성·기존 번호 등록은 `public.issue_warehouse_box_labels` → `app.issue_warehouse_box_labels` 한 트랜잭션에서만 한다. 요청별 잠금과 고유 제약으로 동시 요청을 보호한다. 무작위 값 충돌 시 새 값을 뽑으며 중간 결과는 저장하지 않는다.
- 같은 요청 UUID와 같은 내용의 재시도는 기존 묶음을 돌려준다. 다른 내용으로 재사용하면 오류다. 클라이언트는 결과 불명 시 동일 입력의 요청 UUID를 유지하며, 새로고침 후에도 서버 발급 내역에서 결과를 확인할 수 있다.
- 두 표는 RLS를 켜고 authenticated에는 SELECT만 허용한다. 직접 INSERT/UPDATE/DELETE와 익명 접근은 차단한다. 활성 직원·회사 일치·기존 브랜드 읽기 권한을 검사한다. 발급에는 추가로 기존 브랜드 편집 또는 logistics 업무 권한이 필요하다.
- 내부 SECURITY DEFINER는 고정된 빈 search_path와 명시적 인증·회사·권한 검사를 사용한다. 외부 RPC는 SECURITY INVOKER다.
- 기록은 재사용 방지를 위해 삭제 UI가 없다. 인쇄창 실행을 실제 인쇄 성공으로 기록하지 않는다.

## 검증

- `npm run verify:box-label-registry`: 실제 마이그레이션을 PGlite에 적용하고 숫자 형식, 날짜, 충돌 재시도, 요청 재시도, 전체 롤백, 직접 수정 차단, 회사 경계, 비활성·익명·읽기 전용 권한을 검증한다.
- `npm run verify:warehouse-qr-browser`: 운영 DB 연결을 차단한 별도 PostgreSQL 테스트 저장소와 브라우저로 서로 다른 브라우저의 공유 조회·발급, 응답 유실 후 재시도, 재출력, 기존 QR·엑셀·60×40mm 인쇄를 검증한다. 테스트 데이터는 운영 DB에 넣지 않는다.
- 운영 DB는 새 표의 RLS·고유 제약·함수 권한을 읽어서 확인한다. 보안 advisor에서 새 발급 기록 관련 항목이 없음을 확인했다.
