# 업체별 코드 관리: 표시 이름과 데이터 소유권

## 사용자 동작

- 업체별로 `헤더 설정`에서 표시 이름·설명·순서·표시 여부를 저장한다. 공통 데이터의 원본 필드 이름은 바꾸지 않는다.
- `공통 값 연결`은 바코드, 코드명, 구성품 상품명, M번호를 참조한다. 구성품이 여러 개면 SKU별 M번호와 수량을 모두 표시한다. 이 화면에서는 공통 원본을 편집할 수 없다.
- `업체 전용 항목`은 의미와 입력 형식(문자·숫자·날짜)을 정해 추가하고, 지정 담당자가 코드별 값을 입력한다. 예: 공통 `상품명`을 `물류상품명`으로 표시하고, 무신사 전용 `상품명`을 별도로 입력한다.
- 저장된 항목의 식별자·소스·입력 형식은 고정된다. 삭제 대신 숨기기를 사용해 값과 연결을 보존한다. 연결을 달리하려면 새 항목을 만든다.
- 엑셀 일괄 등록은 기존 코드 연결과 사용 상태만 반영한다. 선택 업체의 코드·상태 표시 이름 및 기존 별칭을 인식하며, 다른 항목의 이름과 충돌하는 별칭은 사용하지 않는다. 공통 값이나 전용 값을 엑셀에서 덮어쓰지 않는다.

## 기존 데이터 보존

`product_codes`, `product_code_components`, `styles`, `code_usage_assignments`, `code_usage_targets`, 기존 `usage_code_columns`의 데이터와 키를 변경하지 않는다. 기존 코드 등록·검수·사용 상태의 처리와 권한은 유지한다.

업체별 설정이 없으면 기존 브랜드 헤더를 읽어 같은 ID·이름·연결로 표시한다. 구형 헤더 테이블도 없는 환경은 기본 다섯 항목으로 표시한다. 조회만으로 설정을 생성하지 않는다. 기존 미확인 항목은 `연결 확인 필요`로 남겨 자동으로 의미를 추정하거나 값을 옮기지 않는다. 명시적으로 저장할 때만 업체별 설정을 생성한다.

## 신규 저장소와 권한

추가 마이그레이션: `supabase/migrations/20261020091506_usage_partner_headers.sql`.

| 저장소                  | 키/역할                                               |
| ----------------------- | ----------------------------------------------------- |
| `usage_partner_columns` | 브랜드 + 업체 + 필드 UUID. 공통 소스/전용 항목 정의   |
| `usage_partner_values`  | 브랜드 + 업체 + 코드 + 필드 UUID. 업체 전용 값만 저장 |
| `usage_partner_editors` | 브랜드 + 업체 + 담당자. 업체별 명시적 편집 권한       |

동일 회사의 활성 사용자에게 기존 브랜드 조회 권한을 추가 확인한다. 관리자·브랜드 책임자는 담당자를 지정한다. 후보는 동일 회사·브랜드의 활성 멤버다. 담당자와 관리자·브랜드 책임자는 기존 브랜드 편집 권한도 충족해야 설정·전용 값을 저장할 수 있다. 담당 해제·브랜드 멤버 해제 후에는 저장할 수 없다. 다른 직원은 읽기 전용이다.

신규 테이블에만 RLS와 권한을 추가한다. 기존 전역 권한 함수를 바꾸지 않는다. 공개 RPC는 SECURITY INVOKER이며 익명 실행을 차단한다. DB 트리거도 공통 값 쓰기, 필드 연결 변경, 부적합 자료형, 업체·브랜드 혼합을 거부한다. 설정과 값 저장은 트랜잭션으로 처리하며 실패하면 일부만 저장되지 않는다.

## 코드 연결

- `UsageCodePage` → `useUsagePartnerSettings` → `usage-partner-settings` → 신규 테이블/RPC.
- `UsageCodeColumnDialog`: 표시 설정·소스 선택·실제 코드 3행 미리보기.
- `UsageCodeValuesDialog`: 공통 연결은 조회만, 전용 값만 입력.
- `UsageCodeManagersDialog`: 이름을 선택해 담당자를 지정.
- `usage-code-columns`: 필드 정규화·검증·엑셀 헤더 식별. `usage-code-display`: SKU별 값 표시.

정확한 파일·심볼·RPC 연결은 `npm run structure:map`으로 생성하는 `dev-tools/structure-map/generated/ai-index.md`에서 확인한다.

## 적용 상태와 검증

**2026-10-20 사용자 승인 후 운영 DB에 추가형 마이그레이션을 적용했다.** Supabase MCP `apply_migration` 성공과 마이그레이션 이력 `20261020091506`을 확인했다. 이전 요청 만료 오류는 이번 요청에서 재현되지 않았으며, 별도 로그인·MCP 권한 변경 없이 적용했다. 로컬 파일명도 실제 적용 이력과 맞춰 이후 중복 적용을 방지한다.

기존 6개 테이블의 행 수와 전체 행 지문을 적용 전후 비교해 모두 동일함을 확인했다. 운영 DB의 `authenticated` 역할과 실제 관리자·일반 직원 프로필을 사용해 RPC를 검증하고 전체 트랜잭션을 롤백했다. 전용 값 저장·조회, 공통 값 수정 차단, 숨김 후 값 유지, 담당자 지정·회수, 다른 업체 수정 및 담당자 자기 지정 차단을 확인했다. 신규 테이블의 검증용 행은 0개다. 기존 헤더나 담당자 설정을 자동 생성하지 않았다.

신규 테이블 3개의 RLS와 공개 RPC 5개의 SECURITY INVOKER·익명 실행 차단도 확인했다. 상세 비교와 기존 보안 진단 항목은 [적용 검증 기록](USAGE_PARTNER_HEADERS_VERIFICATION.md)을 참고한다.

스키마가 없는 다른 환경에서는 기존 코드 목록을 유지하고 신규 설정/전용 값 저장을 비활성화한다. 운영 화면 코드는 PR 병합 전이며, 적용된 DB 기능은 작업 브랜치 미리보기에서 사용할 수 있다.

- `npm run verify:usage-headers`: 필드/값 검증, 기존 ID 보존, 엑셀 소스 식별, 여러 SKU·수량 및 숫자 0 회귀 검사.
- `npm run verify:usage-headers-db`: 독립 PGlite PostgreSQL에 실제 마이그레이션을 적용하고 역할·RLS·RPC 우회·트랜잭션을 검사한다. 기존 공통 테이블의 전후 지문을 비교한다. 운영 DB/인증값은 사용하지 않는다.
- `npm run verify:usage-headers-browser`: 실제 React 페이지에 격리된 데이터 어댑터를 연결해 헤더 이름 변경, 전용 값 편집, 숨김 후 복구, 업체 전환, 담당자 설정, 저장 실패, 읽기 권한, 스키마 미적용을 확인한다. 외부 요청은 차단한다.

DB 검증 런타임은 앱 의존성에 넣지 않는다. 필요하면 무시되는 개발 폴더에 설치한다:

```powershell
npm install --prefix dev-tools/ai-workflow/.state/usage-test --no-save --package-lock=false @electric-sql/pglite@0.5.10
npm run verify:usage-headers-db
```

다른 설치 위치는 `npm run verify:usage-headers-db -- --pglite-path <패키지의 dist/index.js 절대 경로>`로 지정한다. 브라우저 검사는 기존 개발 의존성 `playwright-core`와 로컬 Chrome을 사용하며, 실행 파일 경로는 `ATELIER_CHROMIUM_BIN`으로 지정할 수 있다.

DB 적용은 AGENTS 절차에 따라 별도 승인 후 진행한다. 적용 전에 해당 브랜드의 기존 헤더·업체·코드 연결 건수와 실제 조회 권한을 확인하고, 적용 뒤 동일 ID와 건수를 비교한다. 기존 헤더의 의미가 불명확하면 자동 이관하지 않는다. 신규 테이블 추가만으로 기존 헤더를 덮어쓰지 않는다.
