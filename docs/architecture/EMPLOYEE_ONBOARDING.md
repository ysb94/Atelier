# 신규 직원 등록·서류 관리

## 적용 상태

- 2026-11-03: 로컬 구현·격리 DB·두 화면 브라우저 검증 완료. `20261103102140_employee_onboarding.sql`을 사용자 승인 후 공유 DB에 적용했다. 기존 데이터·함수·정책 보존 검사를 통과했으며 test/main 화면은 배포하지 않았다.
- 원래 폴더·`261102-end`를 유지한다. 공유 DB 연결과 개발자 전용 실제 업로드·다운로드·첨부 해제·저장 후 재조회까지 확인했다.

## 흐름과 권한

- 기존 구글 로그인·본명·가입 승인 경로를 유지한다. 현재 가입 신청자/승인 후 미배치 직원과 앞으로 접수하는 직원만 온보딩 기록을 만든다. 기존 재직자 전체를 등록하지 않는다.
- 승인된 직원은 본인 정보·직원 첨부 5종만 임시 저장/제출한다. G메일과 네이버메일은 모두 필수다. 회사가 입력한 급여·계약 정보는 본인 입력 API에 포함하지 않는다.
- 같은 회사의 활성 운영지원 부서 UUID와 개발자·윤설빈·김준영의 확인된 UUID만 신규 직원 정보를 관리한다. 직책·입력 이메일로 판정하지 않는다. 기존 가입 승인 권한은 확대하지 않는다.
- 부서를 배치해도 미완료 기록은 남는다. 필수서류 오른쪽 완료를 누르면 확인창을 표시하고, 필수정보·회사 정보·서류 제출 여부에 관계없이 완료할 수 있다. 완료한 직원의 My home 입력 버튼은 숨기며, 완료 목록에서 진행 중으로 되돌리면 다시 표시한다. 개발자 테스트도 같은 표시 규칙을 따른다. 기존 입력값·첨부와 사용자 승인 상태는 보존한다.
- 개발자 테스트는 `is_test`인 별도 기록·파일 경로만 사용하며 실제 명부·배치·승인·급여를 쓰지 않는다. 테스트 기록은 개발자 본인만 조회한다.

## 저장과 기존 명부 연결

- `app.employee_onboardings`: 진행 상태, 직원 임시 입력, 회사 입력, 제출/완료 시각·처리자·수정 버전.
- `app.employee_onboarding_files`: 직원 첨부 5종과 서명본 3종, 업로드 확정 여부와 교체 관계.
- `app.employee_onboarding_events`: 처리 종류·직원 기록 ID·처리자·시각만 기록한다. 개인정보 본문은 복제하지 않는다.
- 기존 `employee_roster`의 개인정보·근무·급여 열을 재사용한다. 영문명·예금주·계약기간 등 기존 열이 없는 값은 온보딩 기록에서 보관한다.
- 임시 저장은 명부를 쓰지 않는다. 본인 제출 API는 전화·주민번호·주소·은행·계좌·메일 항목만 서버에서 구성해 반영한다. 일반 직원에게 명부 테이블 권한을 추가하지 않는다.
- 검증된 전용 API 안에서 기존 `app.roster_import` 가드를 한정 사용하고 이전 값을 즉시 복원한다. SQL 예외는 문장 전체를 롤백한다. 기존 명부 가드·RLS·함수는 교체하지 않는다.
- 회사 입력 저장은 관련 명부 필드만 반영한다. 변경 버전과 명부/배치 원본 지문으로 충돌을 검사한다. 연차·비고·로그인·승인·권한 값은 쓰지 않는다.
- 가입 승인 전 회사 정보는 전용 기록에 보관한다. 기존 승인으로 active가 되는 트랜잭션 안에서 준비된 회사 정보를 반영한다. 오류 시 승인을 포함해 롤백한다.
- 서버가 계약기간과 월급·근로유형·기본급·수당을 다시 계산한다. 연봉÷12가 300만원 미만이면 유형1, 이상이면 유형2다. 반올림 전 금액으로 판정한다. 직접 입력 모드는 지정 관리자의 예외 입력으로 보존한다.

## API와 파일

- 공개 API: `get_my_employee_onboarding_status`, `get_employee_onboarding`, `list_employee_onboardings`, `start_employee_onboarding_test`, `save_employee_onboarding`, `set_employee_onboarding_complete`, `begin_employee_onboarding_file`, `finish_employee_onboarding_file`, `remove_employee_onboarding_file`, `get_employee_onboarding_file_path`.
- 공개 함수는 invoker 래퍼다. 실제 저장과 권한 검사는 `app`의 전용 함수에서 처리한다. 전용 표 직접 접근과 익명 함수 실행은 금지한다.
- 비공개 `employee-onboarding` 저장소: PDF/JPEG/PNG, 파일당 10MB, 회사/온보딩 기록/임의 파일 UUID 경로. 원래 파일명은 경로에 넣지 않는다.
- 브라우저는 파일 시그니처를 검사한다. 서버는 등록된 형식·확장자·크기와 실제 Storage 메타데이터를 대조한 뒤 확정한다. MIME 검사는 콘텐츠 악성코드 검사와 동일하지 않다.
- 기존 파일 덮어쓰기는 허용하지 않는다. 새 파일 업로드/확정 성공 후 기존 버전을 연결 해제한다. 동시 교체에서 먼저 반영된 파일을 늦게 끝난 이전 업로드로 덮어쓰지 않는다.
- 연결 해제한 파일은 조회되지 않는다. 삭제 정책은 부여하지 않아 기존 버전과 실패 업로드는 물리적으로 남는다. 별도 보관/정리 정책은 후속 합의 대상이다.
- 다운로드는 권한 재확인 후 인증된 Storage 다운로드를 사용한다. 공개 링크는 만들지 않는다. 계정 전환은 컴포넌트를 새로 만들어 이전 조회·입력·대기 요청의 화면 반영을 정리한다.

## 검증·적용·복구

- `node scripts/verify-employee-onboarding-db.mjs`: 기존 원본/RLS 보존, 관리자/본인/타인/타사/익명, 임시 저장·제출, 서버/브라우저 수식 일치, 승인 전 회사 입력 연결, 버전 충돌·파일 실패·동시 교체·완료·테스트 격리.
- `node scripts/verify-employee-onboarding-browser.mjs`: 외부 통신을 막은 가상 서버의 직원/운영지원 두 화면에서 저장·다시 조회·첨부·출력·완료·되돌리기·PC/모바일을 검사한다. 실제 공유 DB 검증을 뜻하지 않는다.
- Node 22 빌드와 기존 계약서·수식·인쇄 검증을 함께 실행한다. 구조도는 기존 자동 감시로 갱신한다.
- 공유 DB는 사용자에게 표 3개·비공개 저장소 1개·전용 API/보호 함수·프로필 접수/승인 연결 트리거·Storage 정책 2개라는 구체 범위를 확인한 뒤 적용한다. 원본 개인정보를 개발 PC로 내려받는 백업은 만들지 않는다. 서버 정의와 메타데이터를 기록하고, 원본 보존 비교는 DB 내부에서 수행한다.
- 적용은 트랜잭션과 짧은 잠금 제한으로 진행한다. 기존 함수·명부 RLS·조회 정책을 일괄 교체하지 않는다. 실패하면 트랜잭션을 롤백한다.
- 적용 후 실제 권한별 읽기/저장 검증을 수행한다. 운영 직원 상태를 테스트 목적으로 바꾸지 않고 개발자 전용 테스트 또는 롤백 가능한 가상 검증을 사용한다.
- 복구는 새 기능 진입을 보류하고 신규 프로필 연결 트리거만 해제하는 방식으로 준비한다. 이미 제출한 기록과 파일은 보존한다. 원본 명부를 과거 값으로 일괄 복원하거나 테이블/저장소를 삭제하지 않는다.

- 실제 서버의 API 검증은 개발자 테스트 기록에서 실행하고 롤백했다. 브라우저의 실제 Storage 검증에는 개인정보 없는 빈 PDF 1개만 사용했고 첨부 연결을 해제했다. 실제 개발자 명부·급여·승인 상태는 변경하지 않았다.
- 보안 점검에서 이번 변경에 대한 신규 WARN/ERROR는 없었다. 직접 접근을 금지한 app 전용 표 3개의 RLS 무정책 INFO는 의도된 상태다. 상세 접근은 검증된 API만 허용한다.
