# 지각 사유서 첨부 제출과 복구

2026-11-05 클라이언트 수정. 기존 사유서·출근 원본·승인/읽음·RLS·함수 권한·Storage
정책은 유지하며 DB 마이그레이션을 추가하지 않는다.

## 원인과 응답 처리

운영 로그에서 본문 저장(200), 파일 업로드(200), 첨부 완료(204) 뒤 클라이언트의
파일/기록 삭제를 확인했다. Chrome 격리 재현에서도 204의 `body`가 빈 스트림으로
노출되어 진단 래퍼의 `new Response(stream, { status: 204 })`가 예외를 발생시켰다.
기존 실패 정리가 이미 완료된 파일까지 삭제하고 본문만 남겼다.

공통 진단·조회 제한 래퍼는 HEAD와 204·205·304 응답을 재구성하지 않는다.
원래 상태·헤더·취소·조회 제한·재시도 정책은 유지한다.
[MDN Response.body](https://developer.mozilla.org/en-US/docs/Web/API/Response/body),
[Supabase custom fetch](https://supabase.com/docs/reference/javascript/initializing)를 참고한다.

## 첨부 저장

- 기존 준비 RPC → 비공개 Storage 업로드 → 완료 RPC를 사용한다. 완료 응답이
  불확실하면 기존 RLS로 해당 첨부의 `ready` 기록을 조회하고 확인된 성공을 반영한다.
- 실패·확인 실패만으로 파일이나 기록을 자동 삭제하지 않는다. 선택한 File이 살아
  있는 동안 계정·사유서별 준비 ID를 메모리에 유지해 명시적인 재시도에 재사용한다.
  완료된 파일은 재전송하지 않으며, 같은 File의 동시 제출은 진행 중 요청을 공유한다.
- 업로드 응답만 끊긴 재시도는 기존 완료 RPC로 실제 파일 유무를 먼저 검사한다.
  파일이 없다는 서버 응답이 확인된 경우에만 같은 준비 ID로 바이트를 다시 전송한다.
  불명확한 쓰기를 자동 재시도하지 않는다.
- 사용자의 명시적인 파일 제거 동작은 기존 삭제 권한과 절차를 사용한다.
  파일명·내용·직원 식별값을 새 진단에 기록하지 않는다.

## 화면과 기존 본문 복구

새 사유서는 모든 첨부의 완료 후 제출 성공을 안내한다. 본문 저장 이후 오류에는
본문이 저장됐음을 표시하고 기존 본문 입력을 잠근 채 남은 첨부를 재시도한다.
본문은 직원·날짜당 기존 한 건을 계속 사용한다.

제출된 오늘 사유서는 상단의 **지각 사유서 확인**으로 다시 열 수 있다. 활성 상태의
작성자에게만 오늘 사유서의 **첨부파일 추가 → 첨부파일 저장**을 제공한다.
운영지원·타 직원·과거 날짜에는 새 첨부 입력을 제공하지 않는다. 서버의 기존 본인·
오늘 날짜·20MB·5개 제한을 그대로 적용한다. 첨부만 추가할 때 본문을 재저장하거나
승인·읽음 기록을 새로 생성하지 않는다.

이미 삭제된 파일의 원본 바이트는 복원하지 않는다. 직원이 새로고침 후 기존 사유서를
열고 원본 파일을 다시 선택해야 한다. 새 알림 종류나 수신자·승인 권한은 추가하지 않는다.
