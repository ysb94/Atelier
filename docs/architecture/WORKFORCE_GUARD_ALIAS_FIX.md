# 근태·추가 연차 관리 대상 조회의 이름 충돌 수정

## 원인과 범위

2026-11-10 사용자 승인 후 공유 DB에 `20261110092909_workforce_guard_alias_fix`를 적용했다.

11월 5일 관리 대상 구분을 추가하면서 기존 PL/pgSQL 변수와 같은 이름의 SQL 테이블 별칭을 사용했다.

- `app.advance_attendance_presence`: 변수 `c`와 별칭 `c` 충돌로 `c.id is ambiguous` 발생. 주기적인 근무 확인 조회가 실패했다.
- `app.dispatch_extra_leave_grant_notice`: 아직 할당하지 않은 record 변수 `g`와 별칭 `g` 충돌. 추가 연차 등록·수정 이력의 알림 트리거가 실패해 저장 트랜잭션 전체가 롤백됐다.

해결은 해당 조회의 테이블 별칭을 각각 `presence_scope_clock`, `notice_scope_grant`로 바꾸는 것뿐이다. 기존 함수의 나머지 본문·권한·소유자·설정·관리 대상 기준은 유지한다. 마이그레이션은 예상 구문이 없거나 여러 번 나오면 중단하며, 이미 적용됐으면 건너뛴다. 함수 메타데이터가 바뀌면 전체 적용을 실패시킨다.

직원 정보, 기존 연차, 출퇴근 기록, 과거 실패 요청은 직접 수정하거나 재실행하지 않았다. 실패한 추가 연차는 사용자가 내용을 확인한 뒤 다시 저장해야 한다. 프런트엔드 변경이나 main 배포는 필요하지 않다.

## 검증

Node 22.23.4와 로컬 PGlite에서 실행했다. 가상 데이터만 사용한다.

```powershell
node scripts/verify-attendance-presence-db.mjs
node scripts/verify-leave-usage-notices-db.mjs --additional-notices
node scripts/verify-leave-balance-db.mjs --anniversary --additional --fefo --birthday --advance --load-guard --workforce-alias
npm run build
```

- 기존 운영 함수에 실제 11월 5일 관리 대상 조회를 붙여 두 오류를 재현하고, 같은 수정 마이그레이션으로 해소함을 확인했다.
- 예정 퇴근 10분 후 확인, 30분 재확인, 5분 응답, 전달 여부 구분, 연속 5회 무응답 종료, 다음 출근 때 실제 퇴근 시각 입력, 수동 퇴근, 권한 차단을 확인했다.
- 실제 추가 연차 저장 RPC → 이력 → 안내 트리거를 연결해 신규 저장·중복 재시도·수정·부여 취소·권한 차단·기본 연차 보존을 확인했다.
- 기존 연차 차감·취소 복원·기한순 배분·생일 반차·선사용 정산 및 알림 열람·확인·중복 방지 검증을 통과했다.
- 관리 대상 밖 직원 제외, 마이그레이션 재실행 안전성, 함수 권한·설정 보존을 확인했다.
- 운영 적용 전후 함수 정의를 비교해 지정한 별칭 두 곳만 변경되었음을 확인했다. 존재하지 않는 ID 조회도 오류 없이 반환했다. 실제 직원의 연차를 시험 등록하지 않았다.
- 적용 후 한국시간 18:29:18~18:30:39 실제 근무 확인 요청 12건이 모두 HTTP 200으로 응답했다. 같은 조회 구간에 추가 연차 저장 요청은 없었다. 보안 점검의 기존 지적 항목과 건수는 적용 전후 동일했다.

## 백업과 복구

개발 전용 `docs/backups/workforce-alias-20261110/`에 두 함수의 적용 전후 정의·권한과 `restore-functions.sql`을 보관한다. Git에는 포함하지 않는다. 복구가 필요하면 현재 함수가 이 수정 이후 바뀌지 않았는지 먼저 확인하고, 승인된 절차로 원래 정의를 복구한다. 원래 정의로 되돌리면 이번 이름 충돌 오류도 다시 발생한다.
