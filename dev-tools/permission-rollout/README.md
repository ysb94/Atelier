# 권한 전환 사전 점검

운영 DB를 바꾸지 않고 사람별 권한 전환표, 기존 승인자 내역, 부서·직책별 봇과 단계별 적용·복구 자료를 준비한다. 실제 사이트의 라우트·메뉴·배포 번들에는 포함하지 않는다.

## 현재 상태와 실행

- 현재 운영 권한은 기존 방식이다. `VITE_ASSIGNED_PERMISSIONS_ENABLED=false`를 유지한다.
- 실제 사용자·Auth 계정·승인자에 봇을 넣지 않는다. 봇은 UUID가 아닌 `bot:` ID와 `[봇]` 이름을 쓰며 개발용 보고서와 브라우저 메모리에만 존재한다.
- 모든 등록 부서 × 회사별 등록 직책 및 현재 사용 중인 직책을 생성한다. 직책 미지정도 포함한다. 직급은 별도 선택이며 직급 이름을 직책으로 바꾸지 않는다.
- 2026-10-21 읽기 전용 기준: 사용자 9명, 부서 12개, 승인자 지정 4건, 봇 120명. 개인별 이름과 상세 권한은 커밋하지 않는 로컬 보고서에서 확인한다.

Node는 `.nvmrc`의 22를 사용한다.

```powershell
npm run permissions:capture-sql
# 생성한 .tmp/permission-rollout/capture-readonly.sql을 Atelier MCP에서 조회만 한다.
# 반환된 snapshot 객체를 .tmp/permission-rollout/source.json에 저장한다.
npm run permissions:plan
npm run permissions:view
```

뷰어: `http://127.0.0.1:4321/`. DB 연결·쓰기 API·SQL 실행 기능이 없고 GET/HEAD만 받는다. 로컬 보고서가 없으면 성공 화면을 만들지 않는다. 다른 경로·Host를 거부하고 외부 요청·프레임 삽입을 제한한다. 자동화 관리자와 별개이므로 이 뷰어만 실행해도 중지한 노션 업무가 재개되지 않는다.

`permissions:plan`은 Supabase에 연결하지 않고 PGlite의 임시 PostgreSQL에서만 실행한다. `.tmp/permission-rollout/package/`에 다음 자료를 만든다.

| 자료 | 의미 |
| --- | --- |
| `report.json`, `transition.md` | 개인별 현재 코드 기준 권한 → SQL 이관 예정 지정, 추가·제외 및 최초 관리자 후보 |
| `manifest.json` | 원본 SQL·스냅샷 해시, 생성 시점, 로컬 검증 수 |
| `00-preflight-readonly.sql` | 사용자·승인자·기존 연결 및 서버 규칙이 기준 이후 바뀌지 않았는지 조회만 수행 |
| `01-prepare.sql` | 새 권한 저장소·함수·목록만 준비. 기존 함수·정책·트리거 유지, 새 지정 저장 API 잠금 |
| `02-activate.sql` | 같은 트랜잭션에서 최신 기준 확인 → 개인별 이관 → 서버 권한 규칙 전환 |
| `03-rollback-after-activation.sql` | 기존 함수·실행 권한·접근 규칙 복원. 사용자·승인자·업무 행은 덮어쓰지 않음 |

**어떤 명령도 운영 SQL을 실행하지 않는다.** 통합 마이그레이션 파일의 직접 실행도 기본 차단한다. 새 권한 테이블이 이미 있는 스냅샷에는 최초 적용 패키지를 만들지 않는다. 실제 적용·재전환·마이그레이션 이력 처리는 각각 별도 승인 범위다.

## 전환표의 해석

현재 앱의 `legacyPermissionGrants`와 기존 승인자/업체 담당 연결을 준비된 SQL의 실제 이관 결과와 비교한다. 새 권한은 앱의 같은 `permissions.ts` 목록과 판정 함수를 사용한다. 직책·직급만 높은 봇에게는 업무 권한이 없다. 체크한 권한만 가상으로 허용하며 새로고침하면 초기화된다. 범위는 회사 전체로 가정한 모의 실험이고 부서·브랜드·업체·대화방의 서버 검증은 별도 테스트다.

이 표는 **모든 과거 RLS·업무 RPC·Storage·Edge 경로의 실효 권한을 전수 비교한 결과가 아니다.** 자동 이관 누락/확대 후보를 찾는 자료로 쓴다. `permissions.manage` 추가는 기존 관리자에서 가져온 최초 운영 담당 **후보**다. 사용자가 담당자를 확정하기 전에는 이를 승인된 지정으로 취급하지 않는다. 다른 추가/제외가 있으면 이유를 확인하고 전환을 보류한다.

## 적용 단계와 통과 기준

| 단계 | 수행 내용 | 다음 단계 조건 | 실패 시 처리 |
| --- | --- | --- | --- |
| 0. 지금 | MCP READ ONLY 캡처, 전환표·봇·로컬 리허설, 현재 앱/Edge 배포 버전 기록 | 사용자별 차이 확인, 관리자 후보 확정, 운영 적용 별도 승인 | DB 변경 없음 |
| 1. 준비 | 별도 승인과 호환 배포 준비 확인 후 편집·다른 DB 배포를 잠시 중지. 최종 캡처·로컬 검증으로 패키지를 확정하고 `01-prepare.sql`을 트랜잭션 실행 | 기존 함수·정책·트리거 및 보호 대상 행 지문 일치, 새 저장 API 잠금 확인, 기존 로그인·승인자 화면 정상 | 트랜잭션 오류면 전부 취소. 성공 후 중단해도 새 객체는 휴면 상태로 두고 기존 앱 사용 |
| 2. 전환 준비 | 편집 중지를 유지하고 `00-preflight-readonly.sql`로 확정한 기준을 다시 비교 | 아래 호환 배포·복구 준비 모두 확인. 기존 사용자 재가입/재승인 작업은 없음 | 어느 조건이라도 부족하면 기존 방식 유지 |
| 3. 실제 전환 | `02-activate.sql`을 한 트랜잭션으로 실행. 이어 호환 Edge·앱 전환 및 기존 탭 갱신 | 기존 원본 지문 유지, 실제 대표 사용자 로그인·허용/차단 및 승인 기능 확인 | SQL 오류면 전부 취소되어 1단계로 복귀. 커밋 이후 문제면 서버 복구 절차 수행 |
| 4. 안정화 | 사용자·승인자 내역·업무 동작 비교, 변경 이력 확인, 편집 재개 | 사용자 확인 및 배포 검사 완료 | 확인 전 완료·운영 성공 처리 금지 |

### 호환 배포와 복구 준비

1. 로그인 보호 코드를 포함한 **기존 DB와 호환되는 앱 릴리스**를 먼저 준비·검증한다. `main` 병합과 배포는 사용자가 결정한다. 현재 `main` 및 오래 열어 둔 탭이 새 지정 원본을 쓸 준비가 되지 않으면 서버 전환을 하지 않는다.
2. 현재 실제 배포 앱과 `styled-image` Edge의 버전·소스 해시·복구 아티팩트를 보관한다. 저장소의 `origin/main`이 현재 배포 Edge와 같다고 가정하지 않는다. 서버 환경 비밀값은 보고서·커밋에 복사하거나 교체하지 않는다.
3. `01-prepare` 이후 기준을 다시 캡처할 때 새 저장소가 보이면 **최초 패키지를 새로 실행하지 않는다.** 준비 직전 기준 패키지는 보관하고, 보호 대상 데이터·원래 함수/정책이 그대로인지 재조회한다. 바뀌었다면 준비 단계에서 멈춰 기준과 2단계 전용 패키지를 재검토한다. 원래 복구 정의를 새 정의로 덮어쓰지 않는다.
4. 이관 SQL은 기준 이후 사용자 상태·승인자·역량·브랜드 연결·업체 담당·부서·직책·Auth ID 또는 기존 서버 규칙이 바뀌면 중단한다. “검증을 통과하려고” 운영 원본을 스냅샷 값으로 돌리지 않는다. 최신 상태를 기준으로 전환표를 다시 검토한다.
5. 전환 직전 위 확인을 수행한 운영자가 같은 연결에서 `atelier.permission_release_ready`를 `manifest.json`의 `sourceHash`로 설정해야 2단계가 실행된다. 이는 실수 실행 방지용 확인값이며 배포 호환성을 자동 검증해 주는 기능은 아니다. SQL이 달라지면 확인값도 달라진다.
6. 서버 전환 후에는 기존 업체 담당자 저장 API가 중앙 설정을 안내하며 저장을 거부한다. 구버전 화면에서 계속 권한을 편집하게 두지 않는다. **새 앱 스위치만 끈 채로 서버 전환 상태를 장기간 운영하면 안 된다.** 권한 편집 중지와 탭 갱신을 포함한 일괄 전환이 필요하다.
7. 실제 적용 시 새 마이그레이션의 이력 등록도 같이 계획한다. 준비 단계만 끝내고 전체 마이그레이션을 “적용됨”으로 표시하지 않는다. 이 도구는 migration history를 수정하지 않는다.

## 복구 절차

### 준비 중/전환 중 SQL 오류

각 단계는 독립된 트랜잭션이다. 실패하면 해당 연결을 rollback하고 그 단계 전체를 취소한다. 로컬 리허설은 준비 마지막과 전환 마지막에 의도적으로 오류를 넣어 기존 서버 규칙과 사용자·승인자가 그대로 남는 것을 검사한다. 오류를 성공으로 기록하거나 다음 단계로 넘어가지 않는다.

### 준비만 끝내고 중단

기존 모델은 아직 교체되지 않았다. 앱 스위치를 끈 상태로 유지하고 새 저장 API 잠금과 기존 로그인·승인자 화면을 확인한다. 추가된 테이블을 급히 삭제하지 않는다. **전환 후 복구 SQL은 이 단계에서 실행하는 파일이 아니다.**

### 전환 커밋 이후 문제

1. 권한·조직·승인자·가입 승인 편집과 다른 DB 배포를 중지한다. 현재 배포 버전·증상·경로와 **복구 직전의 최신 상태**를 읽기 전용으로 남긴다. 전환 이후 정상적으로 승인되거나 변경된 사용자가 있을 수 있다.
2. 다른 사람이 서버 함수·정책을 변경했다면 저장한 복구 정의로 덮어쓰지 말고 차이를 검토한다. 복구 범위는 이 전환이 바꾼 함수·접근 규칙·트리거로 제한한다.
3. 별도 승인 아래 `03-rollback-after-activation.sql`을 트랜잭션으로 실행한다. 기존 함수 본문·소유자·EXECUTE 허용·정책·RLS 설정을 되돌리고 새 기본 권한 부여 트리거를 제거한다. 새 지정 API/RPC는 잠근다. 새 권한 원본·변경 이력은 남긴다.
4. 확보해 둔 기존 호환 Edge와 로그인 보호 코드를 유지한 앱을 복원한다. 서버 규칙 복원과 앱 전환 사이에는 권한 편집을 열지 않는다. 스위치 변경만으로 복구를 끝냈다고 하지 않는다.
5. **사용자 테이블·승인자 테이블·Auth 사용자·업무 데이터를 과거 백업으로 덮어쓰지 않는다.** 실제 복구 직전과 복구 직후 사용자 승인 상태·승인자·기존 연결이 동일한지 비교한다. 전환 전 사본과 차이가 있더라도 그 사이의 정상 변경을 되돌리지 않는다.
6. 개발자 및 일반 승인 계정 실제 재로그인, 기존 승인자 목록과 검토 동작, 대기/반려/비활성 계정의 접근 차단을 확인한 뒤 편집을 재개한다. 계정 상태에 뜻밖의 변화가 있으면 해당 계정만 원인을 조사하고 별도로 승인받아 복구한다.
7. 새 저장소가 남아 있으므로 같은 최초 SQL을 재실행하지 않는다. 재전환은 원본 지정과 감사 이력을 포함한 새 기준·새 패키지로 따로 검토한다.

전체 DB 초기화, 사용자 재생성, 일괄 승인 변경, 강제 재가입, 테이블 `CASCADE` 삭제는 이 절차에 없다.

## 검증

```powershell
npm run verify:permission-rollout
npm run verify:permission-rollout-browser
npm run verify:assigned-permissions
npm run verify:auth-recovery-browser
npm run verify:page-preview
npm run build
npm run structure:map
npm run verify:structure-map
```

`permissions:plan`은 최신 실제 데이터 사본과 기존 서버 규칙을 로컬에 재현하여 7개 리허설 결과를 보고서에 넣는다. 원본 재현, 준비 장애 취소, 준비 시 기존 모델 보존, 전환 장애 취소, 전환 후 원본 보존, 새 중앙 조회 실행, 서버 규칙 복구를 검사한다. PG 세션 시간대는 UTC로 고정하고 ACL은 허용 내용 기준으로 비교한다.

회귀 검증은 직책·직급 독립, 부서/브랜드/업체 범위, 회사 경계, 본인 지정 금지, 마지막 관리자 보호, 승인자 보존, 가입 승인 시 기본 이용만 부여, 실제 로그인 컴포넌트의 오류/신규 가입 구분과 재신청 차단을 포함한다. **운영에 새 SQL·Edge를 적용한 결과나 다른 실제 직원들의 로그인 완료를 의미하지 않는다.**

상세 원본·개인별 전환표·SQL 복구 정의·실행 결과는 `.tmp/permission-rollout/`에만 둔다. 개인정보·비밀값을 PR·노션·커밋에 넣지 않는다. 새 부서·직책이 생기면 읽기 전용 캡처와 보고서를 재생성한다.
