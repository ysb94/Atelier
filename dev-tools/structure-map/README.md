# Atelier 개발 구조도

앱 코드와 분리된 로컬 개발 도구다. `src`, `public`, 라우터 또는 Vite 설정에 연결하지 않는다.
사이트에 새 페이지를 추가하지 않으며, `npm run build`나 배포 단계에서 실행하지 않는다.

## 열기와 갱신

저장소 루트에서 실행한다. 기존 개발 의존성 TypeScript를 사용하며 추가 패키지나 API 키가 필요 없다.

평소처럼 `npm run dev`를 실행하면 Atelier 개발 서버와 **구조도 변경 감시 서버가 함께 실행**된다.
구조도는 `http://127.0.0.1:4318/`에서 바로 볼 수 있다. 터미널에 두 주소가 표시되며,
`Ctrl+C`로 종료하면 이 명령이 시작한 두 서버를 함께 종료한다. 이미 같은 프로젝트의
구조도 감시 서버가 실행 중이면 재사용하고, 원래 별도로 실행한 서버는 종료하지 않는다.
`npm run dev -- --port=5175` 등 기존 Vite 인수도 그대로 전달한다.
같은 명령으로 노션 개발 자동화 관리자도 함께 켠다. `http://127.0.0.1:4319/health`에서
설정 대기·작업·검토 상태를 확인한다. 인증이 없어도 Atelier와 구조도는 계속 실행한다.
설정과 업무 실행 방법은 `dev-tools/ai-workflow/README.md`를 따른다. 이미 같은 프로젝트의
관리자가 실행 중이면 재사용하며, 이 명령이 시작한 프로세스만 함께 종료한다.
구조도 포트는 `ATELIER_STRUCTURE_PORT` 환경 변수로 바꿀 수 있다.
다른 프로그램이 해당 포트를 쓰면 오류를 콘솔에 알리고 Atelier는 계속 실행한다.
이 연결은 개발 명령에만 적용하며 빌드·배포·운영 앱에는 포함하지 않는다.
구조도 폴더는 Vite 파일 감시에서 제외하므로 구조도 갱신 때문에 Atelier 화면이 다시 로드되지 않는다.

아래 명령은 개발 서버 없이 스냅샷만 만들 때 사용한다.

```powershell
npm run structure:map
```

`dev-tools/structure-map/generated/atelier-structure.html`을 브라우저로 연다.
데이터·스타일·스크립트가 모두 들어 있는 독립 HTML이라 서버나 인터넷 없이 사용할 수 있다.
소스를 바꾼 후 같은 명령을 실행하고 열어 둔 HTML을 새로고침한다.

코드 변경을 자동으로 반영하려면 아래 명령을 실행한다.

```powershell
npm run structure:map:watch
```

콘솔에 표시된 `http://127.0.0.1:4318`을 브라우저에서 연다. **파일로 열어 둔 HTML과는 별개의 보기**다.
2초 간격으로 `src`, `supabase/functions`와 분류·뷰어 소스의 변경을 감지해 재생성하고 화면을 새로고침한다.
감시 서버는 최신 HTML을 메모리에서 제공하므로 브라우저로 열어 둔 파일 스냅샷의 잠금과 무관하게 갱신한다.
파일로 보관할 HTML은 `npm run structure:map`으로 별도 생성한다.
선택한 파일, 펼침, 검색, 확대·이동 상태는 브라우저에 저장해 복원한다.
작업을 마치면 터미널에서 `Ctrl+C`로 종료한다. 앱 개발 서버와는 독립적이다.

포트가 사용 중이면 다음과 같이 바꾼다.

```powershell
npm run structure:map:watch -- --port=4320
```

서버는 `127.0.0.1`에만 바인딩한다. `갱신` 버튼으로 즉시 분석할 수도 있다.
파싱·분류 설정 오류로 생성이 실패하면 콘솔에 이유를 남기고 직전 HTML을 유지한다.
첫 분석이 실패해도 저장된 HTML을 보여 주며 코드 수정을 계속 감시한다. 저장된 HTML도 없으면 분석 대기 화면을 제공한다.
HTML과 `structure.json`은 생성물이며 이 폴더의 `.gitignore`로 버전 관리에서 제외한다.

## 구조도 사용

- `전체 총람`은 공통 기반까지 모든 기능·파일·자원을 펼친 목록이다. 전체 역할을 스크롤로 읽고, 상단 기능 바로가기로 이동하거나 검색으로 좁힌다. 항목을 누르면 지도·코드 상세가 열린다. 총람과 스크롤 위치도 갱신 후 복원한다.
- `지도 모두 펼치기`는 전체 트리를 펼쳐서 보여 준다. 파일 선택 시에도 나머지 기능을 유지한다. 전체를 맞추면 글자가 작아지므로 파일 검색·선택으로 확대하거나 `전체 총람`을 사용한다. `기능 요약`으로 다시 접는다.
- 큰 기능을 선택하면 사용하는 기능과 이 기능을 사용하는 곳을 보여 준다.
- `＋` 또는 `이 기능 중심으로 펼치기`로 기능 중심 지도를 연다.
- 하위 분류를 펼쳐 화면·패널·훅 / 업무 로직 / 데이터 접근 / 서버 / 데이터 자원을 확인한다.
- 지도·검색·기능의 코드 목록에는 한글 기능명과 역할을 먼저 표시한다. 파일명과 경로는 파일 선택 후 상세에서 확인한다. 파일명으로 검색하는 기능은 유지한다.
- 파일을 선택하면 직접 import, API 위임, 테이블·RPC·Storage·Edge 호출과 역방향 참조를 볼 수 있다.
- 연결의 접힌 상세를 열면 파일 경로·줄 번호·import 이름과 API 경유 근거를 확인할 수 있다.
- 화면명, URL 패턴, 파일 경로, 공개 함수 이름, 테이블·RPC 이름으로 검색할 수 있다.
- 지도 빈 곳을 드래그해 이동한다. 휠은 이동, `Ctrl+휠`은 확대·축소한다.
- `기능 요약`은 선택·펼침을 초기화한다. `화면 맞춤`은 현재 지도를 화면 안에 맞춘다.
- 파랑 화살표는 사용하는 방향, 주황 화살표는 선택한 코드가 사용되는 방향이다. 회색 선은 폴더 분류다.
- 타입 전용 연결과 API 허브·공통 셸 등의 기반 연결은 기본 숨김이다. 상세에는 공통 기반 파일도 표시한다.
- 경로 복사와 VS Code 링크를 제공한다. VS Code 링크는 로컬 PC에 해당 프로토콜이 등록되어 있어야 한다.

지도에서 접혀 있는 파일의 연결은 보이는 상위 노드로 모아 표시한다.
파일을 선택하면 같은 분류의 다른 파일을 접어 선택 파일과 주변 연결에 집중한다.
`이 기능의 전체 코드 보기`를 누르면 전체 파일 트리로 돌아간다.
연결 수는 파일 사이 관계 수이며 실행 횟수나 호출 빈도가 아니다.

## 분석 기준과 한계

TypeScript AST로 현재 **작업 디렉터리**를 분석하므로 아직 커밋하지 않은 변경도 포함된다.
분석 결과는 생성 시점의 스냅샷이며 운영 사이트 상태와 반드시 같지는 않다.

자동 분석 범위:

- `src`와 `supabase/functions`의 TS/JS 코드. 테스트·verify·선언 파일 제외.
- `@/`, 상대 경로, index 파일의 import·export, 타입 전용 연결과 문자열 리터럴 동적 import.
- `new Worker(new URL('상대경로', import.meta.url))`의 Web Worker 연결.
- `company-routes.tsx`, `App.tsx`의 Route 경로, 중첩 경로, 로컬 JSX 래퍼·lazy 컴포넌트와 대상 파일.
- `company-workspace-nav.ts`의 메뉴명과 Route 패턴을 연결. 메뉴 권한에 따른 실제 노출은 계산하지 않는다.
- 명시적 `.from`, `.rpc`, `.storage.from`, `.functions.invoke` 호출의 자원 이름과 줄 번호.
  같은 파일의 문자열 상수 이름도 해석한다. 테이블 조회·수정 동작 자체나 SQL 조인 대상은 구분하지 않는다.
- `src/lib/api/index.ts`의 공개 함수에서 namespace 메서드에 위임한 저장소와 named re-export.
  소비 화면이 **가져온 함수** 기준이다. 그 함수의 실제 실행 여부, 인수, 조건 분기나 호출 순서는 추적하지 않는다.

특히 API 허브 전체를 지나가는 단순 전이 추적은 사용하지 않는다. 예를 들어 화면이
`getStylesByBrand`를 가져오면 `styles.ts`에 위임하는 근거를 보여 주며, API 허브가 가져온
다른 저장소까지 그 화면의 실제 호출로 단정하지 않는다. 원래의 파일 import도 별도로 보존한다.

포함하지 않는 것:

- 모든 함수의 세밀한 호출 그래프, 런타임 실행·성능 프로파일, 조건부 분기 여부.
- 동적으로 계산한 자원·import 이름, SQL/RPC 내부 테이블 관계, Realtime 구독 관계.
- 실제 DB 스키마, RLS, 데이터, Auth 세션, 환경 변수·키.
- 마이그레이션, 검증 스크립트, 별도 앱이나 개발 도구의 코드.

해석하지 못한 동적 호출·로컬 import는 첫 화면의 `분석 범위와 누락 확인`에서 확인한다.
큰 기능 설명은 개발 문맥을 위한 수동 분류이며, 실제 연결의 근거는 코드 경로와 줄 번호다.
새 기능은 자동으로 발견하며 분류 규칙이 없으면 `미분류`에 둔다.

## 한글 기능명과 역할 설명

파일별 목록과 연결을 하드코딩하지 않는다. 매 분석 때 현재 소스에서 다시 생성한다.

- 화면의 정적 `PageHeader` 제목 → 연결된 메뉴명 → 파일의 주요 한글 제목 순서로 기능명을 추출한다. 보조 함수의 대화상자 제목이나 여러 카드 중 하나를 파일 전체의 역할로 단정하지 않는다.
- 화면 안내 문구가 있으면 역할 설명으로 가져온다. 코드에서 확인한 화면 항목도 상세에 표시한다.
- 제목이 없는 파일은 `labels.mjs`의 공통 용어 사전으로 이름을 한글화하고, 위치·종류·공개 함수 이름으로 역할을 추정한다. 송장 코드의 `product-name`은 품목명, `item-name`은 내품명으로 표시한다.
- 상세의 `기능명·역할은 어떻게 정해졌나요?`에서 자동 추출과 추정을 구분하고, 제목 근거의 파일·줄 번호를 확인할 수 있다. 모르는 용어는 의미 확인이 필요한 조각으로 표시한다.

일반 앱 코드 변경·파일 추가/삭제·화면 제목 변경은 감시 모드에서 자동 반영된다.
파일별 설명을 따로 관리할 필요는 없다. 큰 기능의 분류 규칙은 `domains.json`, 새 용어의
공통 해석은 `labels.mjs`에서 보완한다. 분석기 등 도구의 실행 코드를 바꾼 경우에는
감시 서버를 다시 실행한다. 추정 설명은 사람이 읽은 완전한 기능 명세를 대신하지 않는다.

## 분류 변경

`domains.json`의 `domains`에서 기능명·설명과 아래 규칙을 수정한 뒤 갱신한다.

| 키 | 적용 대상 |
| --- | --- |
| `features` | `src/features/<이름>` |
| `libs` | `src/lib/<이름>` |
| `stores` | `src/lib/supabase/<파일명>`의 정확한 이름 또는 접두어 |
| `functions` | `supabase/functions/<함수명>` |
| `shared` | `supabase/functions/_shared/<파일명>`의 접두어 |
| `infrastructure` | 지도에서 기본 숨길 공통 기반 연결 |

중복 규칙은 목록의 첫 일치를 사용한다. 테이블·RPC 등 자원은 직접 참조한 파일이
가장 많은 기능 아래에 배치한다. 이는 DB 소유권/RLS의 구분이 아니라 보기용 분류다.
회사/브랜드 경계와 M번호의 SKU 의미는 `docs/architecture/SUPABASE.md`, `AGENTS.md`를 따른다.

## 검증

```powershell
npm run verify:structure-map
npm run structure:map
```

테스트는 임시 소스 fixture에서 별칭·중첩 Route·lazy 화면·API 위임·데이터 호출과
타입 분리, 한글 제목·역할 추출과 소스 수정 시 갱신을 검증한다. 운영 DB를 조회하거나 변경하지 않는다.
