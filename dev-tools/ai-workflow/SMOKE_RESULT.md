# 노션 개발 자동화 사용 안내

이 문서는 노션 업무를 PC의 Cursor로 작업하고 Codex로 검토하는 **개발 전용 도구**의
사용 방법을 정리한다. 운영 앱의 화면·라우트·배포 번들에는 포함되지 않으며, 운영 DB를
수정하는 용도로 쓰지 않는다. 자세한 규칙은 같은 폴더의 `README.md`를 기준으로 한다.

> 이 문서는 사용 안내이며 실제 연결 시험의 성공 여부를 기록하지 않는다.
> 실제 실행 결과는 노션 업무 본문·`AI 결과`와 `.state/runs` 기록에서 확인한다.

## 1. `npm run dev`로 함께 실행되는 것

`npm run dev`는 `dev-tools/structure-map/dev.mjs`를 실행하며 다음 세 가지를 함께 띄운다.

| 대상 | 주소 | 비고 |
| --- | --- | --- |
| Atelier 개발 서버(Vite) | Vite 기본 주소 | Vite 종료 시 이번 명령이 시작한 서버도 종료된다. 재사용한 기존 서버는 유지된다 |
| 개발 구조도 | `http://127.0.0.1:4318/` | `ATELIER_STRUCTURE_PORT`로 변경 가능 |
| 자동화 관리자 | `http://127.0.0.1:4319/health` | `config.json`의 `port`(로컬은 `config.local.json`) |

- 같은 프로젝트의 구조도·자동화 관리자가 이미 실행 중이면 새로 띄우지 않고 재사용한다.
- 구조도나 자동화 관리자가 종료되거나 설정을 읽지 못해도 Vite 개발 서버는 계속 실행된다.
- 개발 서버 없이 관리자만 실행하려면 `npm run ai:watch`를 쓴다.
- 관리자는 한 번에 한 업무만 실행한다. PC가 꺼져 있거나 절전 중이면 실행되지 않는다.

## 2. 상태 확인과 「설정 대기」일 때 확인할 항목

`http://127.0.0.1:4319/health`의 `state` 값으로 상태를 본다.

- `연결 확인 중`: 관리자가 막 시작해 첫 점검을 하는 중이다.
- `설정 대기`: 아래 점검 중 하나 이상이 실패했다. `problems`에 이유가 표시된다.
- `설정/연결 확인 필요`: 점검은 통과했지만 노션 연결 등에서 오류가 났다.
- `대기`: 실행할 업무를 기다리는 중이다. 작업 중에는 `작업 중`·`검토 중`이 표시된다.

`설정 대기`일 때는 `npm run ai:doctor`로 같은 점검을 직접 실행할 수 있다.
`problems`에 나오는 항목별 조치는 다음과 같다.

1. **`NOTION_TOKEN 미설정`**: Notion Developer portal에서 관리자용 내부 연결을 만들고
   대상 업무 DB를 그 연결에 공유한다. `.env.example`을 참고해 이 폴더의 `.env.local`에
   `NOTION_TOKEN`을 넣는다. 토큰은 노션 페이지·대화·`VITE_*` 변수·Git에 넣지 않는다.
   관리자는 다음 확인 주기에 파일 변경을 다시 읽는다.
2. **`Cursor CLI 로그인 필요`**: `npm run ai:login`을 실행한다. 편집기 로그인과 CLI
   로그인은 별개일 수 있다. CLI 실행 파일을 찾지 못하면 공식 Cursor Windows CLI를
   `.runtime/cursor/package/dist-package`에 두거나 `.env.local`의 `ATELIER_CURSOR_BIN`으로 지정한다.
3. **`Codex CLI 확인 실패`**: Codex CLI 설치와 인증을 확인한다. 기본 명령(`codex`)이 아니면
   `.env.local`의 `ATELIER_CODEX_BIN`으로 지정한다.
4. **`Cursor MCP 설정/플러그인을 찾지 못했습니다`**: 사용자(`~/.cursor/mcp.json`)·프로젝트
   (`.cursor/mcp.json`) MCP 설정이나 Cursor 플러그인 설정이 있는지 확인한다.
   설정을 찾은 것은 연결 성공의 증거가 아니므로 실제 도구 호출로 인증을 확인한다.
   대시보드 팀 MCP는 ACP 지원 대상이 아니며, CLI에서 OAuth 재로그인이 필요할 수 있다.
   서비스별 인증 확인과 로그인 방법은 아래 「5. 세 가지 인증 설정의 차이」를 따른다.

점검을 통과한 뒤 `노션 속성이 없습니다: …` 오류가 나면 업무 DB에 `config.json`의
`properties`에 적힌 속성(예: `AI 자동 실행`, `AI 상태`, `AI 요청`)이 모두 있는지 확인한다.

## 3. 노션에서 업무를 「대기」로 지정해 자동 실행하는 방법

관리자는 `AI 자동 실행`이 체크되어 있고 `AI 상태`가 `대기`인 업무만 가져오며,
`AI 실행 순서`가 낮은 업무부터 하나씩 실행한다.

1. `AI 요청`: 할 작업을 구체적으로 적는다.
2. `AI 완료 기준`: 보존할 동작, 확인할 결과와 필요한 검증을 적는다.
3. `AI 허용 파일`: 프로젝트 기준 상대 경로를 줄바꿈 또는 쉼표로 1~30개 적는다.
   절대 경로, 프로젝트 밖 경로, `.git`·`.cursor`·`node_modules`·`.env*`·`.runtime`·`.state`
   경로와 인증 파일, `supabase/`·`docs/backups/` 경로는 허용되지 않는다.
4. `AI 실행 순서`: 숫자를 넣는다. 비워 두면 가장 뒤로 밀린다.
5. `AI 자동 실행`을 체크하고 `AI 상태`를 `대기`로 지정한다.

실행 중 동작과 주의할 점:

- 대기 업무 확인 주기는 기본 30초(`pollMs`, 최소 10초)이고, 작업 중 중지 확인은 10초마다 한다.
- 지시·보고·검토 기록은 업무 본문에 회차별로 추가되며 원래 본문은 덮어쓰지 않는다.
  `AI 결과`에는 최근 요약, `AI 반복 횟수`에는 회차가 표시된다.
- Cursor 작업 → 검증 스크립트 실행 → Codex 읽기 전용 검토 순서로 진행하며,
  수정 지시와 재작업은 최초 작업을 포함해 최대 3회까지다.
- 작업 중 `AI 요청`·`AI 완료 기준`·`AI 허용 파일`을 바꾸면 확인 필요로 중단된다.
- 중지하려면 `AI 상태`를 `중지`로 바꾸거나 `AI 자동 실행` 체크를 해제한다.
- 중단된 업무는 파일 변경과 오류를 확인하고 `AI 요청`을 갱신한 뒤 다시 `대기`로 지정한다.
  같은 지시 내용의 완료·중단 기록은 자동으로 다시 실행하지 않는다.
- 자동화 지시로 커밋·푸시·배포를 하지 않는다. DB 스키마·삭제·대량 수정은
  `docs/architecture/SUPABASE.md`의 승인·백업 규칙을 따른다.

## 4. Cursor와 관리자의 역할 분담

자동 실행에서 Cursor는 **파일 읽기·검색과 허용 파일 편집만** 한다. 변경 범위 확인,
검증 명령 실행, 구조도 갱신은 관리자가 Cursor 작업이 끝난 뒤 직접 수행한다.

| 담당 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| Cursor(ACP 세션) | 구조도에서 전달받은 범위의 파일을 읽고, `AI 허용 파일`만 편집하고, 결과를 보고한다 | 터미널 명령 실행(`git status`·`npm` 등), 허용 파일 밖 수정, 커밋·푸시·배포 |
| 자동화 관리자 | 작업 전후 파일을 비교해 변경 범위를 확인하고, 구조도 갱신과 검증 스크립트를 실행하고, 실제 로그를 Codex 검토에 전달한다 | 범위 밖 변경을 자동으로 되돌리기 |
| Codex(읽기 전용) | 요청·완료 기준·실제 diff·검증 결과를 기준별로 검토한다 | 파일 수정 |

- 관리자는 Cursor 세션을 터미널 기능 없이 연결하므로 Cursor에 터미널 명령을 요청하지 않는다.
  알 수 없는 도구 요청은 자동 승인하지 않고 `도구 확인 필요`로 중단한다.
- Cursor가 허용 파일 밖의 경로에 쓰려 하면 `허용 범위 밖 수정 요청`으로 중단된다.
- 작업 시작 시점의 파일을 기록해 두므로, 기존 미커밋 변경과 이번 작업의 변경을 구분한다.
  검증·검토 도중 코드가 바뀌면 최신 코드로 다시 확인하도록 중단한다.
- 관리자가 실행하는 검증은 `npm run structure:map`(구조도 갱신)과 `config.json`의
  `verificationScripts`(현재 `lint`, `build`, `verify:diagnostics`, `verify:structure-map`)다.
  검증 명령은 개발자만 변경한다.
- 검증 통과, 기준별 증거, 실제 파일 변경이 모두 있어야 완료로 기록된다.

## 5. 세 가지 인증 설정의 차이

자동화에는 서로 다른 인증 설정 세 가지가 필요하다. 하나를 마쳤다고 다른 설정이
자동으로 해결되지 않는다.

| 설정 | 쓰는 곳 | 설정 방법 |
| --- | --- | --- |
| Cursor CLI 계정 로그인 | 관리자가 Cursor CLI(ACP 세션)를 실행할 때의 Cursor 계정 인증 | `npm run ai:login` |
| 관리자용 `NOTION_TOKEN` | 관리자가 노션 업무를 조회하고 결과·상태를 기록할 때 쓰는 내부 연결 토큰 | 이 폴더의 `.env.local`에 입력(「2. 상태 확인」의 1번 항목 참고) |
| 개별 MCP OAuth 로그인 | Cursor 작업 세션이 노션·Supabase MCP 도구를 호출할 때의 서비스별 인증 | `npm run ai:mcp:login -- notion` 또는 `npm run ai:mcp:login -- supabase` |

- 편집기(Cursor 앱)에 로그인했거나 편집기에서 MCP OAuth를 연결했더라도 CLI에 자동으로
  공유된다고 가정하지 않는다. CLI 로그인과 MCP 로그인은 각각 확인한다.
- `NOTION_TOKEN`은 관리자 전용이다. Cursor의 원격 노션 MCP OAuth 로그인과는 별개이므로
  토큰을 넣어도 노션 MCP 로그인이 필요할 수 있고, 그 반대도 마찬가지다.

MCP 인증 상태 점검과 로그인 순서:

1. `npm run ai:mcp:status`로 서비스별 실제 인증 상태를 확인한다.
2. 상태가 `requires_authentication`인 서비스는 `npm run ai:mcp:login -- notion`
   (또는 `supabase`)을 실행하고 브라우저에서 로그인한다. 서비스별로 하나씩 진행한다.
3. 다시 `npm run ai:mcp:status`로 상태가 바뀌었는지 확인한다.

- 이 도우미는 IDE의 MCP 설정 파일을 바꾸지 않고, 비밀값 없는 공개 HTTPS 서버 주소만
  `.runtime`의 격리된 점검 폴더에 기록한다. OAuth 비밀값은 복사하지 않는다.
- 비밀 헤더가 있거나 주소에 인증값이 포함된 MCP 서버는 이 로그인 도우미의 대상이 아니다.
- 위 명령은 사용자가 직접 실행한다. 자동 실행 중인 Cursor 세션에는 이 명령을 요청하지 않는다.

## 6. Cloudflare 제외

Cloudflare MCP는 사용자 요청으로 자동화 대상에서 제외했다. `config.json`의
`excludedMcpServers`에 `cloudflare`가 등록되어 있으며, 다음에서 모두 빠진다.

- 자동화의 Cursor 플러그인 로딩과 ACP 작업 세션의 MCP 연결 구성
- `npm run ai:doctor` 연결 점검의 MCP 목록
- `npm run ai:mcp:status` 점검과 `npm run ai:mcp:login` 로그인 대상

따라서 Cloudflare 로그인은 필요하지 않으며, 자동화 업무에 Cloudflare 작업을 지정하지 않는다.
다시 포함하려면 사용자 결정에 따라 개발자가 `excludedMcpServers` 설정을 변경해야 한다.
