# Atelier 노션 개발 자동화

노션 `E&J 메모·작업 카드`의 메모를 GPT(Codex CLI, ChatGPT 구독)가 실제 소스와 구조도로 판단·계획하고,
빠른 Cursor가 구현만 맡으며, GPT가 실제 코드를 다시 검토한다. 합격한 작업은 카드마다 독립된
Git 작업 브랜치로 커밋·푸시하고 통합 브랜치 대상 PR을 만든다. 자동 병합은 하지 않는다.
운영 앱·라우트·배포 번들에는 연결하지 않는 개발 전용 도구다.

`config.json`의 `v2.enabled: true`가 이 흐름(v2)이다. `false`이면 예전 실행기(`runner.mjs`/`parallel.mjs`)가
호환용으로 동작한다. 예전 실행기의 메모 자동 분류(직접 할 일로 보내기)는 제거했다.

## 실행과 연결

`npm run dev`가 Vite, 구조도(4318), 자동화 관리자(4319)를 함께 실행한다.
`http://127.0.0.1:4319/health`에서 `workflow`, 설정값, 접수 상태(`admission`), 진행 작업, 오류 목록을 확인한다.
연결이 없으면 자동화만 대기하고 개발 서버는 계속 실행한다.
개발 서버 없이 관리자를 실행하려면 `npm run ai:watch`, 연결 점검은 `npm run ai:doctor`다.
같은 프로젝트의 기존 관리자는 재사용한다. v2 파이프라인은 계획·검수를 함께 처리하는 GPT 공용 실행 자리 2개와 Cursor 구현 자리 2개를 실행한다.
PC가 꺼지거나 절전 중이면 실행되지 않는다. 다시 켜면 미전송 노션 기록부터 재전송하고 중단된 작업을 이어간다.

필요한 최초 설정:

1. Cursor CLI 로그인: `npm run ai:login`. 편집기 로그인과 CLI 로그인이 다를 수 있다.
2. Notion Developer portal에서 관리자용 내부 연결을 만들고 업무 DB와 설정 페이지를 연결에 공유한다.
3. `.env.example`을 참고해 이 폴더의 `.env.local`에 `NOTION_TOKEN`을 넣는다.
   토큰은 노션 페이지·대화·`VITE_*`·Git에 넣지 않는다. 관리자가 파일 변경을 다음 확인 주기에 읽는다.
4. Cursor 프로젝트/사용자 MCP와 로컬 노션·Supabase 플러그인의 기존 공개 서버 정의를
   격리된 CLI 작업 폴더에서 사용하고, ACP 작업 세션이 해당 CLI 연결을 재사용한다.
   IDE 설정 파일을 바꾸거나 OAuth 비밀값을 복사하지 않는다.
   CLI에서 OAuth 재로그인이 필요할 수 있다. 설정 발견은 연결 성공의 증거가 아니다.
   대시보드 팀 MCP는 ACP 지원 대상이 아니다. 사용자/프로젝트 MCP 인증과 실제 도구 호출을 확인한다.
5. Codex CLI는 ChatGPT 구독 계정으로 로그인한다. 계획과 검토는 별도 읽기 전용 실행이며 Codex 대화창을 조작하지 않는다.
6. GitHub CLI 로그인: `gh auth login`. 작업 브랜치 푸시는 `origin`의 Git 인증을 쓰고, PR 생성·상태 조회는 `gh`를 쓴다.
   `origin`의 가져오기·게시 주소가 모두 `v2.remoteUrl`(`https://github.com/ysb94/Atelier.git`)과 같아야 한다.
   다르면 어떤 Git 작업도 하지 않는다. 다른 `gh` 실행 파일은 `.env.local`의 `ATELIER_GH_BIN`으로 지정한다.
7. 노션 준비(아래 설정 페이지·업무 DB 속성)를 마치고 `config.json`의 `v2.controlPageId`에 설정 페이지 ID를 넣은 뒤
   관리자를 다시 시작한다. `npm run ai:doctor`의 `v2Setup`에 정확한 속성 이름·형식과 기본값이 나온다.

Codex는 구독 로그인만 사용한다. 관리자는 시작 시와 매 GPT 호출 전에 `codex login status`를 확인하고,
API 키·미로그인·확인되지 않은 방식이면 호출하지 않는다. 모든 GPT 호출(계획·검토)에
`forced_login_method="chatgpt"`와 `model_provider="openai"`를 지정해 API 과금 경로로 전환하지 못하게 한다.
API 키 요구, 크레딧 구매, 다른 공급자로의 자동 전환은 없다. 구독 사용량 부족·인증 오류는 `자동화 단계 오류`로
이유를 남기고 멈춘다. Codex 구독 사용량은 CLI와 앱에서 합산된다. Cursor 요금제 설정은 별도로 관리한다.

Cursor 계정 로그인과 MCP 서비스 로그인은 별개다. `NOTION_TOKEN`은 관리자가 업무를 조회·기록할 때 쓰며,
Cursor의 원격 노션 MCP OAuth 로그인은 별도다. `npm run ai:mcp:status`로 실제 서비스 인증 상태를 확인하고,
`requires_authentication`이면 `npm run ai:mcp:login -- notion`(또는 `supabase`)을 실행해 브라우저에서 로그인한다.
IDE 설정은 변경하지 않으며 공개 서버 주소만 `.runtime`의 격리된 점검 폴더에 기록한다.
Cloudflare는 사용자 요청으로 `excludedMcpServers`에 등록해 플러그인 로딩·ACP 연결·점검·로그인 대상에서 제외했다.

공식 Cursor Windows CLI를 `.runtime/cursor/package/dist-package`에 설치하면 자동 발견한다.
다른 실행 파일은 `.env.local`의 `ATELIER_CURSOR_BIN`, `ATELIER_CODEX_BIN`으로 지정한다.

## 노션 준비

### 설정 페이지 (`v2.controlPageId`)

관리자는 페이지를 만들지 않는다. 운영자가 데이터베이스 행 하나(또는 속성이 있는 페이지)를 만들고 아래 속성을 정확히 둔다.

| 속성 | 형식 | 비어 있을 때 |
| --- | --- | --- |
| GPT 모델 | 선택 | 오류. 기본 모델로 대체하지 않음. 예: `gpt-6.1-sol` |
| GPT 추론 | 선택 | 오류. `low`·`medium`·`high`·`xhigh`·`max`. `minimal`은 그 모델 카탈로그에 있을 때만 (`gpt-6.1-sol`) |
| Cursor 모델 | 선택 | 오류. 기본 모델로 대체하지 않음. 현재 기본 표기 `grok-4.7-xhigh-fast` |
| 자동화 실행 | 체크박스 | 꺼짐이면 새 작업을 받지 않음 |
| 기준 브랜치 | 텍스트 | `save/automation-progress-20261013` |
| 통합 브랜치 | 텍스트 | `integration/automation-review` |
| 실행 상태 | 텍스트 | 관리자가 기록(실행 중·일시 중지·중지 이유, 진행 작업) |

브랜치 텍스트가 비어 있을 때만 `config.json`의 `v2.defaults`를 쓴다. 모델·추론 선택이 비어 있으면 오류이며 기본 모델로 실행하지 않는다.
모델 목록은 자주 바뀌므로 이름 허용 목록을 두지 않는다.
영문·숫자와 `. _ : -`만으로 된 이름이면 그대로 전달하고, 제공자가 거부하면 그 오류를 보이게 멈춘다(다른 모델로 대체하지 않음).
속성 누락·형식 오류·잘못된 값·기준과 통합 브랜치가 같음·`main` 같은 보호 브랜치를 통합 브랜치로 지정하면
새 작업을 받지 않고 `실행 상태`와 `/health`에 이유를 남긴다.

### 업무 DB

- `위치` 선택지: `메모`, `답변 완료`, `자동화 할 일`, `자동화 작업 중`, `검토 중`, `확인 필요`, `완료`.
  `검토 중`은 선택 사항이다(`positions.reviewing: null`이면 검토도 `자동화 작업 중`에 표시).
  `직접 할 일`은 v2에서 쓰지 않는다. 남은 카드는 운영자가 `메모`·`확인 필요` 등으로 옮긴다.
- 추가 속성: `GitHub 브랜치`(텍스트), `GitHub PR`(URL), `반영 상태`(선택: `통합 대기`·`통합 검수 중`·`main 반영 완료`),
  `실행 모델`(텍스트), `기준 커밋`(텍스트). 관리자는 시작 시 이름·형식·선택지를 확인하고 없으면 시작하지 않는다.
- `자동화 단계`에는 `중지`·`오류`·`확인 필요`·`완료`와 진행 표시(`구조 확인`·`대기`·`작업 중`·`검토 중`·`수정 중`)가 필요하다.

## 흐름

1. 사용자가 메모(제목·본문)를 쓰고 `화면`을 선택한다(`영역`은 선택). 화면이 비어 있는 메모는 작성 중으로 보고 건드리지 않는다.
2. GPT가 원문 제목·본문·내 답변과 실제 사이트 소스·구조도를 읽고 판단한다.
   - 사용자 결정·자료·직접 처리가 필요하면 본문 끝에 `Atelier AI 확인 필요 안내`(멈춘 이유, 질문, 사용자 작업)를 쓰고
     `확인 질문`·`작업 결과`를 채운 뒤 `확인 필요`로 옮긴다.
   - 충분하면 `AI 요청`·`AI 완료 기준`·`AI 허용 파일`·`실행 모델`·`GitHub 브랜치`·`기준 커밋`을 쓰고 `자동화 할 일`로 옮긴 뒤 바로 구현을 시작한다.
3. 사용자는 `내 답변`에 답하거나 직접 처리한 결과를 적고 `답변 완료`로 옮긴다. GPT가 다시 판단해 질문이 남으면 `확인 필요`,
   충분하면 `자동화 할 일`로 진행한다. `확인 필요`에 그대로 있는 카드는 다시 보지 않는다.
4. 구현: GPT가 이번 회차의 상세 실행 지시를 새로 쓰고, Cursor는 그 지시대로 허용 파일만 편집한다(판단·질문·터미널 없음).
5. 검사·검토: 관리자가 검사 스크립트를 실행하고, GPT가 실제 코드·diff·검사 로그로 검토한다.
   합격이면 게시 후 `완료`, 수정이면 GPT가 새 지시를 써서 Cursor가 다시 구현(최초 포함 `maxAttempts`회).
   횟수를 다 써도 코드·검사 문제이면 사용자 질문이 아니라 `자동화 단계 오류`로 멈추고 편집은 남긴다. GPT가 사용자 결정이 필요하다고 한 경우에만 `확인 필요`.
6. 다른 카드는 계속 진행한다(최대 두 개).

`v2.cursorPull.enabled`이면 `자동화 할 일`은 완성된 실행 지시서의 목록이다. GPT는 준비 과정에서 카드를 `GPT 준비`에 두고, 질문이 남으면 `확인 필요`, 계획과 원문·코드 해시를 저장한 뒤에만 `자동화 할 일`로 옮긴다. 계획 담당은 여기서 실행 자리를 반환한다. Cursor 실행기는 GPT 스캔과 별개로 5초마다 이 목록을 조회해 빈 구현 자리에 배정한다. 조회·배정에는 모델을 호출하지 않는다.

- 지시서가 없는 카드, 원문이 바뀐 카드, 오류 카드는 Cursor 목록에서 `GPT 준비`로 돌린다. 사용자 본문·답변·기존 편집·브랜치·오류 표시는 보존한다. 준비된 작업을 먼저 확인하고 잘못 들어온 카드는 회당 최대 2개 정리한다.
- Cursor 시작 직전에 코드 해시를 확인한다. 코드가 바뀌었으면 구현 전에 준비 단계로 돌아가며, 재계획 없이 낡은 지시로 실행하지 않는다.
- 검수에서 보완 지시가 나오면 같은 브랜치의 `자동화 할 일`로 다시 올린다. 같은 파일의 예약은 재작업 대기 중에도 유지한다. 사용자 질문은 `확인 필요`로 보낸다.
- 새 메모나 답변은 `메모`/`답변 완료`로 올린다. `자동화 할 일`에 직접 올려도 준비 지시서가 없으면 먼저 `GPT 준비`로 이동한다.

파이프라인 카드 선택 순서: `검토 중` → `자동화 작업 중`(중단 복구) → 준비된 `자동화 할 일` → `GPT 준비` → `답변 완료` → `메모` (`cursorPull` 사용 시). 같은 위치에서는 `실행 순서`, 생성일 순이다. GPT의 각 실행 자리는 한 건을 마친 뒤 검수 대기를 다시 확인한다. 계획 전 업무는 노션에 남겨 두며 공용 GPT 실행 자리의 수를 넘겨 선접수하지 않는다.

### 단계별 병렬 실행

- `v2.pipeline.gptWorkers: 2`: GPT 계획·검수에 공용 실행 자리 2개를 둔다. 두 자리 모두 계획하거나, 두 자리 모두 검사·검수하거나, 하나씩 처리할 수 있다. 계획과 검수 합계는 항상 2개 이하이며 Cursor 구현 2개는 별도다. 같은 설정 모델을 업무별 세션으로 호출하며 구독 사용량은 함께 소모한다. `gptWorkers`가 없으면 예전 단계별 고정 한도를 사용한다.
- 계획이 끝난 지시서는 Cursor 대기열에 둔다. 구현이 끝나면 Cursor 실행 자리를 즉시 반환하고 검사·검수 대기열로 이동한다. 검수에서 수정 지시가 나오면 같은 브랜치로 Cursor 대기열에 다시 들어간다.
- 준비된 지시서 대기가 4개면 새 계획을 기다린다. 실행 중인 검사·검수와 검수 대기의 합이 3개 이상일 때도 새 계획을 기다려 검수 누적을 줄인다.
- 검수 대기가 있으면 새 계획보다 먼저 처리한다. 실행 중인 GPT 호출은 중간에 끊지 않는다. 검수가 실행 자리를 받아 대기가 없으면 남는 GPT 자리에서 다음 계획을 준비할 수 있다.
- 실행·대기를 포함해 관리자가 접수하는 업무는 최대 8개다. 대기 중에는 모델을 호출하지 않는다. `/health`의 `pipeline`에 단계별 실행·대기·한도가 표시되며 노션 설정의 실행 상태에도 건수를 기록한다.
- 같은 허용 파일을 수정하는 업무는 구현 시작부터 검수·게시 또는 중단까지 순서대로 처리한다. 각 업무는 독립 worktree를 사용하며, 파일 충돌이 없는 업무는 대기열의 다른 항목을 지나 진행할 수 있다.
- Cursor 시작 직전에 원문·답변·작업 공간 해시를 다시 확인한다. 오래된 지시서는 다시 계획하고 기존 편집을 보존한다.
- 질문이나 오류가 발생하면 실행 자리를 반환한다. 재시작하면 저널의 단계와 브랜치로 대기열을 재구성하며 구현 호출 전 대기는 구현 완료로 간주하지 않는다.
- `pipeline.enabled`가 꺼져 있으면 기존의 업무 단위 동시 실행 제한(`maxParallelTasks`)을 사용한다. 변경한 병렬 한도는 관리자 재시작 후 적용된다.
판단은 최신 원문·답변·코드와 이전 회차 변경을 기준으로 한다. 입력·코드·모델이 모두 같은 성공 응답은 재사용한다. 예전 AI 요청·완료 기준·허용 파일은 지시로 물려받지 않는다.
원문 본문과 내 답변은 바꾸지 않는다. 자동 생성 콜아웃(확인 필요 안내, 실행 식별이 붙은 안내, 완료 보고서, 예전 `Atelier AI 메모 분류`)과 제목이 `Atelier AI <식별자>`인 예전 실행 기록 토글만 원문 버전에서 제외한다. `Atelier AI`로 시작하는 사용자 문단은 원문에 포함한다.

### GPT 계획·검토의 자료

- Codex CLI는 `--sandbox read-only`, 셸·앱 도구를 끈 상태로 실행하고 `--model`과 `model_reasoning_effort`를 지정한다.
  선택한 모델·추론 강도는 계획과 검토 모두에 쓴다.
- 계획은 `화면`의 정확한 경로/화면명으로 진입 파일을 고른다. 넓은 `영역` 단어로 여러 기능의 전체 소스를 묶지 않는다. 직접 의존 파일은 경로·가져온 이름 목록만 제공한다.
- 작은 파일은 원문, 큰 파일은 관련 줄 구간·함수 위치·파일 전체 해시를 보낸다. `complete=false`에는 읽지 않은 구간이 있음을 명시한다. 계획 소스는 파일당 12,000자·합계 60,000자, 전체 계획 프롬프트는 100,000자 한도다.
- 검토는 전체 diff와 실제 검사 결과, 변경 구간과 주변 코드, 필요한 의존 코드를 사용한다. 큰 파일의 변경 구간은 생략하지 않는다. 검토 소스는 파일당 24,000자·합계 80,000자, 전체 프롬프트는 140,000자 한도다. 변경되지 않은 의존 코드까지 모두 읽었다고 간주하지 않는다.
- GPT가 꼭 필요한 추가 소스를 요청하면 최대 `v2.maxSourceRounds`(기본 2)회 더 읽는다. `src/example.ts#L100-L180`처럼 정확한 줄 범위를 요청할 수 있다. 기존 구간과 새 구간을 합친 작은 자료를 보내며, 이미 받은 전체 파일/같은 요청만 반복하면 새 호출 전에 멈춘다. 없는 파일은 "제공 불가"로 알린다.
- 한도를 넘으면 모델을 호출하기 전에 `자동화 단계 오류`로 멈춘다. 누락된 근거를 추측해 합격시키지 않는다. `.env*`·`.state`·인증 자료는 넣지 않는다.
- 계획 형식이 잘못되면 이유를 붙여 한 번 다시 요청하고, 두 번 연속 실패하면 오류로 멈춘다.

### GPT 반복 소모 방지와 사용량

- 성공한 JSON 응답은 프롬프트·실제 코드 해시·모델/추론·출력 스키마가 모두 같을 때만 재사용한다. 회차 ID나 구조도 생성 시각만 바뀌어도 다시 호출하던 동작을 없앴다. 재사용 이후에도 최신 노션 원문과 파일 해시를 확인한다.
- 동일 입력의 실제 호출은 최대 2회다. 호출 전에 횟수를 저장하여 관리자 재시작으로 제한을 우회하지 않는다. 중단/응답 유실도 소모 가능성이 있어 횟수에 포함한다. 원인 해결 후 관리자가 해당 `.attempts.json` 기록을 확인해야 하며, 카드만 계속 옮겨도 호출 한도를 초기화하지 않는다.
- 각 실행 폴더의 `gpt-usage.jsonl`에 단계, 모델/추론, 입력 문자 수, 호출/완료/중단/재사용과 CLI가 반환한 입력·캐시 입력·출력 토큰을 기록한다. 사용량을 반환하지 않은 실행은 `null`이다. 프롬프트와 비밀값은 이 지표에 넣지 않는다. 구독의 남은 비율/금액을 계산하거나 API 과금으로 전환하지 않는다.
- 노션이 0폭 문자 링크를 제거해 자동 안내를 새 사용자 원문으로 오인하던 문제를 수정했다. 자동화가 쓴 블록 ID를 쓰기 응답에서 즉시 기록하고, 응답 유실 복구용 링크도 표시 가능한 문자를 사용한다. 사용자가 복제한 별도 블록은 원문으로 보존한다.

### 모델 기록

E&J 상단의 `자동화 실행 현황`은 전체 실행/일시정지, GPT 계획·Cursor 구현·GPT 검수의 실행/대기 건수와 모델을 30초마다 표시한다. 진행 업무의 고정 모델이 새 작업 설정과 다르면 두 값을 함께 표시한다. `대기`는 실행 자리에서 할 일을 기다리는 상태다. GPT 검수의 `검사·검수 중`에는 모델 검토 전 로컬 검사도 포함된다.

Cursor는 상단에 `Cursor 1`, `Cursor 2`를 따로 표시한다. 각 실행 자리에 모델·업무 제목·진행 상태를 보여주며, 한 업무가 계속 구현 중이면 조회 순서가 바뀌어도 같은 번호를 유지한다. 구현 지시서 대기와 GPT 검사·검수로 넘어간 업무는 실행 자리를 차지한 것으로 표시하지 않는다. 설정 페이지의 `Cursor 1 상태`, `Cursor 2 상태`에도 같은 값을 저장한다. 두 번호는 동시 구현 실행 자리이며 별도 컴퓨터를 의미하지 않는다.

GPT 공용 실행을 사용하면 상단은 `GPT 1`, `GPT 2`로 표시한다. 각 자리의 현재 역할(계획 또는 검사·검수), 고정 모델/추론, 맡은 업무를 보여준다. 실행 자리를 반환하면 다른 업무가 같은 번호를 받는다. 업무가 모두 질문·오류·보류 대기이면 두 자리 모두 대기하며, 목록 점검만 반복하고 빈 GPT 호출은 만들지 않는다.

- 설정 페이지 속성: `GPT 계획 상태`, `Cursor 구현 상태`, `GPT 검수 상태`(텍스트), `최근 연결`(날짜), `실행기 연결`(Notion 수식).
- `실행기 연결` 수식은 마지막 연결이 2분 이상 오래되면 `연결 확인 필요`를 표시한다. 전체 실행 환경이 꺼지면 상단의 마지막 기록도 그대로 남으므로 갱신 시각과 수식 표시로 판단한다.
- `v2.statusDashboard.blockId`는 관리자가 갱신할 기존 표시 블록이다. 표시 프로세스는 HTTP health와 로컬 저널·설정만 읽고 노션 표시 속성과 해당 블록만 갱신한다. GPT/Cursor 호출이나 업무/답변/모델 설정 변경은 없다.
- `ai:watch` 시작 시 표시도 시작하며 별도 잠금으로 중복 실행을 막는다. 실행 중인 관리자를 재시작하지 않고 붙일 때는 `node dev-tools/ai-workflow/status-dashboard.mjs`를 실행한다. 독립 실행하면 관리자가 꺼졌을 때도 연결 끊김을 표시한다.

- 새 카드(또는 새 회차)는 시작할 때 설정 페이지 값을 복사해 쓴다. 진행 중인 작업은 도중에 설정을 바꿔도 처음 값으로 끝까지 간다.
- Cursor에는 `--model`로 별칭을 지정한다. `grok-4.7-xhigh-fast`는 기본 모델 `grok-4.7`, 추론 `xhigh`, fast `true`다.
  ACP `initialize`의 `clientCapabilities._meta.parameterizedModelPicker`는 `true`여야 한다. 없으면 레거시 목록이 추론을 high로 보고할 수 있다.
  세션 `configOptions`의 `model`·`reasoning_effort`·`fast`를 읽고, 다르면 `session/set_config_option`(`sessionId`, `configId`, `value`)으로 맞춘 뒤 반환된 값을 다시 확인한다.
  요청한 값과 유효 값이 다르면 그 세션을 거부한다. 추론을 조용히 낮추지 않는다. 로그와 `실행 모델`에는 유효 모델·추론·fast를 적는다.
  별칭에 매개변수가 없는 모델만, configOptions가 없을 때 기존 `session/set_model`로 확인한다.
- 인쇄 모드를 쓰지 않는다. 샌드박스는 끄지 않고 `HOME`도 바꾸지 않는다. `CURSOR_SANDBOX_POLICY_DIR`만 이 도구의 쓰기 가능한 `.runtime/cursor-sandbox-policy`를 가리킨다.

## 멈춤의 세 종류

| 구분 | 노션 표시 | 원인 | 재개 방법 |
| --- | --- | --- | --- |
| 일시 중지 | 설정 페이지 `실행 상태` | `자동화 실행` 꺼짐 | 다시 켠다. 진행 중이던 작업은 끄는 동안에도 끝까지 진행한다. |
| 사용자 질문 | `위치=확인 필요`, `자동화 단계=확인 필요`, 본문 안내 | 사용자만 답할 수 있는 결정·자료·직접 처리 | `내 답변`을 적고 `답변 완료`로 옮긴다. |
| 환경 오류 | `자동화 단계=오류`, `작업 결과`에 이유와 처리 방법 | 로그인·네트워크·GitHub·노션·모델 사용 불가·자료 한도 등 | 일시 오류는 자동 재시도, 운영자 조치가 필요한 오류는 조치 후 `자동화 단계`를 `대기`로 바꾼다. |

- 환경 오류는 사용자 질문으로 만들지 않는다. 카드는 원래 위치(작업 중·검토 중이었다면 `자동화 할 일`)에 남고 `자동화 단계=오류`, `작업 결과`에 구체적 이유를 적는다.
  새 메모·할 일의 기본 단계가 `대기`여도 첫 실패(작업 공간·Git·연결)는 그 카드에 남긴다. 동일 실패 이벤트의 전달 재시도만 중복 기록하지 않는다. 사용자가 대기로 되돌린 후 새 실패가 발생하면 새로운 이벤트로 이유를 기록한다.
- 일시 오류는 5분부터 두 배씩 최대 120분 간격(`v2.retryMinutes`·`maxRetryMinutes`)으로 재시도하며 시각을 `작업 결과`에 적는다.
  성공하거나 질문으로 넘어가면 실패 횟수를 초기화한다.
- 운영자 조치 오류: Codex·Cursor·GitHub 로그인, Git 작성자 설정, `origin` 불일치, 자료 한도, 계획 형식 반복 오류,
  검토 이후 변경 감지, 작업 공간 유실 등. 조치 후 `자동화 단계=대기`로 바꾸면 같은 단계에서 이어간다.
- 모델 사용 불가: 그 카드는 오류로 멈추고 같은 모델 조합으로는 새 작업도 받지 않는다(`실행 상태`에 표시).
  설정 페이지에서 모델을 바꾸면 새 작업 접수가 풀리고, 멈춘 카드는 `자동화 단계=대기`로 바꾸면 바뀐 모델로 이어간다.
- `자동화 단계=중지` 또는 카드를 자동화 위치 밖(`확인 필요`·`완료` 등)으로 옮기면 10초 안에 그 작업을 멈춘다.
  게시(커밋·푸시·PR·완료 기록)도 각 단계 전에 원문 버전·실행 식별자·위치·중지를 확인한다.
  원문이 바뀌거나 카드가 작업 중·검토 중을 떠나면 이미 끝난 게시만 기록하고 완료로 덮어쓰지 않는다.
  같은 작업 브랜치에서 최신 요청을 다시 계획한다.
- 작업 중 제목·본문·화면·내 답변이 바뀌면 그 회차를 버리고 최신 원문으로 다시 계획한다.
  노션 조회가 불안정하면 구현이나 합격을 진행하지 않고 다시 시도한다.

## 복구와 기록

- 진행 상태는 `.state/state.json`의 `v2.jobs`(카드별)에 회차(cycle) 단위로 저장한다.
  단계: 계획 → 계획 완료 → 구현 → 검사 → 검토 → 게시 → 게시 완료. 결과: 확인 필요·오류·중지·최신 원문으로 교체·완료.
- 관리자를 멈추거나 PC가 꺼져도 단계는 남는다. 다시 시작하면 같은 원문이면 그 단계부터 이어간다.
  구현 중이었다면 Cursor를 다시 부르지 않고 작업 공간의 실제 변경으로 검사·검토한다.
- GPT 계획 응답은 입력(프롬프트·모델·전체 코드 해시) 단위로 `.state/runs/<runId>/plan-<key>.json`에 남긴다. `.cache.json`의 입력/출력 해시가 일치하는 완료 응답만 재사용하며, 중단된 응답 파일만 존재하는 경우는 성공으로 간주하지 않는다.
- 확인 필요·완료·오류는 회차 상태와 노션 outbox 이벤트를 한 번의 저널 저장으로 남긴다.
  재시작 때 그 이벤트만 없으면 outbox에 다시 넣는다. 노션 쓰기 실패는 재시도만 하고 코드를 다시 만들지 않는다.
  같은 검토의 커밋을 다시 쓰는 조건은 저장된 검토 SHA, 현재 HEAD, 검토한 내용 해시가 모두 같을 때뿐이다.
  이전 커밋 뒤에 새 수정이 있으면 그 브랜치에 후속 커밋을 만든다. 기준 커밋의 조상 관계, 검토 HEAD, 내용 해시, 게시한 SHA는 회차마다 남긴다.
  완료된 카드의 새 답변은 기존 작업 브랜치와 기준 커밋을 유지하고 새 회차로 계획한다.
- 노션 쓰기는 로컬 outbox에 순서대로 쌓아 카드별로 보낸다. 쓰기 직전과 안내·보고서 추가 직전에 현재 실행, 원문 버전, 위치, 중지를 다시 확인한다.
  이전 실행의 완료·질문·오류는 새 카드 상태를 바꾸지 않는다. 같은 실행의 완료·질문 저장이 중간에 끊기면 그 카드에서 이어서 기록한다.
  Notion API는 조건부 갱신을 지원하지 않으므로 마지막 조회와 쓰기 사이의 동시 변경까지 완전히 막지는 못한다.
- 완료된 카드를 `메모`로 옮기면 이전 기록을 `v2.history`에 보존하고 새 실행·새 브랜치로 시작한다. `답변 완료`·`자동화 할 일`로 옮기면 같은 실행·브랜치에서 새 회차를 시작한다.
- 생성 블록은 확정된 block ID로 식별한다. nonce는 응답이 유실되어 ID가 없는 대기 기록의 복구에만 사용한다. 사용자가 복제한 블록은 원문으로 보존하며, 삭제된 생성 블록의 소유권 기록은 폐기 상태로 유지한다.
- 질문·완료를 기록하는 동안 원문이 바뀌면 해당 이벤트를 취소하고 최신 요청을 같은 브랜치에서 다시 계획한다. 이미 사용자가 바꾼 위치와 답변은 보존한다.
- 이전 회차의 판단·질문·검토 요약은 카드 기록의 `history`에 남기고 다음 계획에 참고 자료로 전달한다.
- 프롬프트·Cursor 대화·검사 증거·검토 JSON·PR 본문은 `.state/runs/<runId>`에만 둔다. 비밀값은 기록 전에 가린다.

## 브랜치·PR

- 작업마다 브랜치 `auto/<페이지 ID 앞 8자>-<runId 앞 8자>`를 만든다. 이 이름은 실행이 바뀌기 전까지 고정된다.
- 첫 회차에서 `origin`의 기준 브랜치를 가져와(fetch) 그 커밋 SHA를 `기준 커밋`으로 고정한다. 사용자의 현재 작업 폴더·미커밋 변경은 쓰지도 바꾸지도 않는다.
- 작업 공간은 프로젝트 밖 Git worktree다. 이 저장소의 `v2.workspaceRoot`는 `/workspace/.atelier-task-worktrees`다.
  설치된 `node_modules`는 링크로 재사용한다. 확인 필요 → 답변 완료 → 재계획 동안 같은 브랜치·작업 공간·이전 편집을 유지한다.
- 검사와 GPT 검토는 작업 공간 안에서 한다. 허용 파일 밖 변경은 지우거나 되돌리지 않는다.
  `자동화 단계 오류`로 파일 목록을 남기고, 단계를 대기로 바꾸면 GPT가 그 파일을 계획에 넣어 유지 또는 되돌림을 지시한다.
  구조도 생성물(`dev-tools/structure-map/generated/`)은 관리자 산출물이라 작업 변경으로 보지 않는다.
- 합격하면 허용 파일 안의 변경만 커밋하고 강제 없이 푸시한 뒤 `gh pr create --body-file`로 통합 브랜치 대상 PR을 만든다.
  통합 브랜치가 원격에 없을 때만 기준 커밋으로 만든다. PR 본문에는 노션 카드, 기준 커밋, 실행 모델, 변경 파일, 검사, GPT 검토와 사용자 보고서가 들어간다.
- 변경 없이 검증만으로 합격한 작업은 이유를 완료 보고서에 쓰고 브랜치 게시·PR을 만들지 않는다.
- 자동 병합은 없다. `main`에 커밋·푸시·병합하지 않으며 강제 푸시도 하지 않는다. `-`로 시작하거나 잘못된 브랜치 이름, `main`을 작업·통합 브랜치로 쓰는 설정은 거부한다.
- 완료 후 HEAD와 미커밋 변경을 확인해 깨끗한 작업 공간만 정리하고 브랜치·PR은 남긴다. 검토 이후 변경이 발견되면 작업 공간을 보존하고 정리 경고를 기록한다.

### 통합과 main 반영 상태

- 운영자 전용 명령으로 통합한다. 승인은 실행할 때마다 명시하며 저장하지 않는다.
  통합 브랜치를 생략하면 노션 설정 페이지의 `통합 브랜치`를 읽는다. `--integration=`은 그 실행에서만 덮어쓴다.

  ```
  node dev-tools/ai-workflow/integrate.mjs list
  node dev-tools/ai-workflow/integrate.mjs merge --approve-integration --pr=<번호>@<전체 head SHA>
  node dev-tools/ai-workflow/integrate.mjs review
  ```

  `list`와 `merge`는 선택한 통합 브랜치를 대상으로 하는 같은 저장소의 열린 PR을 다룬다. `auto/`만 고르지 않는다.
  다른 저장소에서 온 PR은 `--allow-cross-repo`가 있을 때만 포함한다. 그때는 head 저장소 주소를 확인하고 그 저장소의 승인한 SHA만 가져온다.
  합치기는 GitHub PR 병합 API를 쓰지 않는다. 승인한 head SHA를 격리된 작업 공간에서 통합 브랜치 끝에 로컬 머지한 뒤,
  그 통합 ref가 머지 시작 시점의 커밋과 같을 때만 `--force-with-lease`로 그 ref를 갱신한다. 결과는 그 커밋의 후손이어야 하며 main에는 푸시하지 않는다.
- `review`는 병합 뒤 통합 검수다. 설정 페이지의 GPT로, 통합 브랜치를 fetch해 SHA를 고정하고
  `/workspace/.atelier-task-worktrees/integration-reviews/<sha>`에 분리된 detached 작업 공간을 만든다.
  설정된 검사를 실행하고, 기준 브랜치 대비 변경의 소스 묶음으로 GPT가 검토한다.
  기록은 `dev-tools/ai-workflow/.state/integration-reviews/<sha>.json`과 설정 페이지 `실행 상태`, `/health`의 `integrationReview`에 남는다.
  합격은 그 SHA에만 유효하다. 통합 브랜치가 다른 커밋으로 움직이면 상태는 `통합 검수 무효`가 되고 이전 SHA 기록은 그 커밋에만 남는다.
  이 명령은 main에 병합하지 않는다. main 반영은 GitHub에서 따로 승인한 PR 병합이다.
- 관리자는 10분(`v2.reconcileMinutes`)마다 GitHub를 읽기 전용으로 조회해 `반영 상태`를 갱신한다.
  PR head가 `origin/main`에 있으면 `main 반영 완료`, 통합 브랜치에 들어갔거나 GitHub에서 병합됐으면 `통합 검수 중`, 열린 채로 통합 브랜치에 없으면 `통합 대기`.
- 한계: squash·rebase로 main에 반영하면 커밋이 달라 `main 반영 완료`를 감지하지 못하고 `통합 검수 중`에 머문다.
  닫힌 PR은 더 추적하지 않는다. main 반영 상태를 추정해서 적지 않는다.

## 완료 보고

- 본문 끝에 비전공자용 완료 보고서를 남긴다: 메모 출처, 바뀐 점, 사용 방법, 실제 확인 결과, 브랜치·PR·기준 커밋·반영 상태, 완료 시각.
  운영 사이트 게시로 표현하지 않는다. 같은 기록을 재전송해도 중복 생성되지 않는다.
- `완료일`에 한국 날짜, `자동화 완료 시각`에 분 단위 시각을 저장한다. 보고서와 로컬 기록에는 초까지 남긴다.
- 사용자가 완료 기록 전송 전에 카드를 다시 옮겼다면 위치는 바꾸지 않고 브랜치·PR 속성과 결과만 기록한다.

## 안전 규칙

- Cursor는 ACP로 실행하며 허용 파일만 쓰게 한다. 터미널·Git·DB·노션 쓰기·배포를 맡기지 않는다.
- MCP 도구는 자동 승인하지 않는다. SQL 실행·마이그레이션·알 수 없는 요청은 거부한다.
  DB 스키마·삭제·대량 수정은 `docs/architecture/SUPABASE.md`의 승인·백업 규칙을 따른다.
- 검사 명령은 `config.json`의 `verificationScripts`와 GPT가 고른 등록된 `verify:*` 스크립트다. 개발자만 목록을 바꾼다.
  로컬 설정이 필요하면 `config.local.json`에 포트·확인 간격 등을 지정한다.
- 검증: `npm run verify:ai-workflow`. 이 테스트의 Cursor/Codex/Notion은 테스트 대역이며 실제 연결 시험과 구분한다.

`verify:browser-images`, `verify:browser-deadline`, `verify:browser-attendance`는 Playwright와 Chromium으로
실제 화면 컴포넌트의 등록·수정·표시를 검사한다(Chromium 경로는 `ATELIER_CHROMIUM_BIN` 또는 `/usr/bin/chromium`).
검사 전용 Vite 서버만 테스트 프로필·오프라인 응답을 쓰며 외부 네트워크와 DB 쓰기는 차단한다.
실제 계정 로그인·RLS·DB 지속성은 이 검사로 확인할 수 없다.

## 실제 연결 시험 기록

2026-10-12, `E&J 공통 할 일`의 합성 시험 업무
[자동화 연결 시험: 개발 도구 안내 문서 작성](https://app.notion.com/p/3f763ce0dccd813eb5acd35563a7da97)을 실행했다.
Cursor가 `SMOKE_RESULT.md`를 보완했고, 독립 Codex 검토에서 서버 종료 설명의 오류를 찾아
수정 지시를 노션에 기록했다. Cursor가 해당 문장을 수정한 뒤 2회차 검토에서 합격했다.
관리자가 `AI 상태=완료`, `진행=완료`를 기록했으며 노션에서 다시 조회해 확인했다.
두 회차 모두 구조도 갱신·lint·build·진단·구조도 검증을 통과했고, 이번 작업의 변경은 안내 문서 한 파일뿐이었다.
운영 업무·DB 데이터 조회와 변경은 시험에 포함하지 않았다.
별도 CLI 인증을 마친 후 노션·Supabase는 `ready` 상태와 도구 목록을 확인했다.
실제 Cursor ACP 세션에서도 합성 시험 페이지 하나를 노션 MCP로 읽어 제목·완료 상태를 확인했다.
Cloudflare는 사용자가 연결을 원하지 않아 인증을 중단하고 자동화 대상에서 제외했다.
이 문서 작업의 완료가 업무·DB 데이터 조회 시험의 완료를 의미하지는 않는다.
Cloudflare 제외와 CLI 연결 재사용을 적용한 최종 구성에서도 같은 안내 문서의 인증 설명을
Cursor가 보완하고 검증 5개·독립 Codex 검토를 통과했다. 노션의 두 완료 속성을 재조회해 확인했다.
자동화 제어 회귀 검증 15개도 통과했다.

v2(GPT 주도·브랜치/PR 게시)는 아직 실제 연결 시험 기록이 없다.
